# 一、项目介绍类问题

## 1. 你这个项目是做什么的？

- 问题：请你简单介绍一下这个 12306 项目。
- 为什么会问到这个问题：这是项目面试的开场题，面试官想先判断你是否真的理解项目定位，而不是只背技术栈。
- 对应项目中的哪个部分：根目录 `pom.xml`、`services/pom.xml`、`services/user-service`、`services/ticket-service`、`services/order-service`、`services/pay-service`、`services/gateway-service`。
- 回答思路：可以说这是一个模拟铁路 12306 核心购票链路的 Java 微服务项目，核心链路包括用户登录、乘车人管理、车票查询、购票选座、订单创建、支付回调、超时关闭、取消和退款。项目采用 Maven 多模块结构，业务服务拆成网关、用户、车票、订单、支付，公共能力拆到 `frameworks` 下面。
- 可能的延伸追问：为什么要拆成这些服务？你主要负责或最熟悉哪一块？这个项目和普通 CRUD 项目最大的不同是什么？

## 2. 这个项目的核心业务链路是什么？

- 问题：用户从查票到支付成功，后端发生了哪些事情？
- 为什么会问到这个问题：面试官会用这题判断你是否能把多个服务串起来，而不是只知道单个接口。
- 对应项目中的哪个部分：`TicketController`、`TicketServiceImpl`、`TrainSeatTypeSelector`、`TicketOrderRemoteService`、`OrderServiceImpl`、`PayServiceImpl`、`PayResultCallbackOrderConsumer`、`PayResultCallbackTicketConsumer`。
- 回答思路：登录后网关透传用户信息；查票时车票服务从缓存和数据库组合出车次、价格、余票；购票时先责任链校验，再按席别选座并锁座；车票服务远程调用订单服务创建待支付订单；订单服务投递 RocketMQ 延迟关闭消息；支付服务创建支付单并接收支付宝回调；支付成功后通过 MQ 通知订单服务改订单状态、通知车票服务把座位改成已售。
- 可能的延伸追问：为什么创建订单和支付成功后的状态更新不放在一个同步事务里？如果支付成功消息重复消费怎么办？

## 5. 这个项目和普通后台管理系统有什么区别？

- 问题：这个项目难点在哪里？
- 为什么会问到这个问题：面试官想判断你是否理解业务复杂度，而不是把项目讲成普通增删改查。

- 回答思路：普通后台系统主要是低并发 CRUD，而这个项目的核心是高并发查票和购票。查票要求读性能，购票要求库存准确，订单要求状态可靠，支付要求异步回调和幂等处理，超时未支付还要自动释放资源。因此它更考验缓存设计、并发控制、消息驱动和一致性处理。

# 二、基础知识结合项目的问题

## 6. 项目里 ThreadLocal 用在什么地方？

- 问题：你们怎么在业务代码里拿到当前登录用户？
- 为什么会问到这个问题：ThreadLocal 是 Java 基础高频点，项目里正好有用户上下文场景。
- 对应项目中的哪个部分：`frameworks/bizs/user/src/main/java/core/UserContext.java`、`UserTransmitFilter.java`。
- 回答思路：网关解析 Token 后把用户 ID、用户名、真实姓名放进请求头；下游服务的 `UserTransmitFilter` 从请求头取出用户信息，放入 `UserContext`。`UserContext` 底层使用 `TransmittableThreadLocal`，比普通 ThreadLocal 更适合在线程池或异步任务中传递上下文。请求结束后在 finally 中清理上下文，避免线程复用导致脏数据。
- 可能的延伸追问：ThreadLocal 为什么会内存泄漏？为什么这里要 finally remove？TransmittableThreadLocal 和 ThreadLocal 区别是什么？

## 7. JWT 在这个项目里怎么用？

- 问题：项目登录态是怎么实现的？
- 为什么会问到这个问题：认证授权是后端面试常见问题，也能自然连接网关、Redis 和用户上下文。
- 对应项目中的哪个部分：`UserLoginServiceImpl.login`、`frameworks/bizs/user/toolkit/JWTUtil`、`gateway-service/filter/TokenValidateGatewayFilterFactory.java`。
- 回答思路：用户登录时，用户服务根据用户名、手机号或邮箱找到用户并校验密码，成功后生成 JWT，返回 `accessToken`，同时把登录响应缓存到 Redis 30 分钟。网关对需要登录的路径校验 Authorization，解析 JWT 后把用户信息透传给下游。业务服务再通过用户上下文获取当前用户。
- 可能的延伸追问：只解析 JWT 是否足够？如何实现 Token 续期和踢下线？JWT 泄露怎么办？

## 8. 项目里事务是怎么使用的？

- 问题：你们哪些操作用了事务？为什么？
- 为什么会问到这个问题：事务是 Java 后端基础高频，面试官会结合订单创建、支付回调这种真实业务追问。
- 对应项目中的哪个部分：`OrderServiceImpl.createTicketOrder`、`OrderServiceImpl.cancelTickOrder`、`PayServiceImpl.commonPay`、`PayServiceImpl.callbackPay`、`TicketServiceImpl.executePurchaseTickets`。
- 回答思路：订单创建时要同时写订单主表、订单项、乘客关联表，并投递延迟关闭消息，使用本地事务保证同一服务内数据一致。取消订单要同时更新订单和订单项状态。支付创建要写支付单。车票购票里保存车票和远程创建订单在一个方法中声明事务，但远程调用不属于本地事务，所以这块要关注跨服务一致性，主要靠异常回滚、延迟关闭和补偿思路兜底。
- 可能的延伸追问：Spring 事务什么时候会失效？远程调用失败本地事务能不能回滚？跨服务事务你会怎么设计？

## 9. AOP 在项目里有什么实际应用？

- 问题：项目里有没有用到 AOP？解决了什么问题？
- 为什么会问到这个问题：AOP 是 Spring 高频基础，项目里的幂等组件正好是典型应用。
- 对应项目中的哪个部分：`frameworks/idempotent/src/main/java/com/guoxu/core/IdempotentAspect.java`、`@Idempotent` 在购票、支付、乘车人、MQ 消费中的使用。
- 回答思路：项目封装了 `@Idempotent` 注解，通过 AOP 拦截标记的方法。切面读取注解配置，根据场景 RESTAPI 或 MQ、类型 SpEL 等选择不同处理器，在业务执行前生成幂等 key 并校验重复请求，业务成功后做后置处理，异常时清理幂等标记。这样业务代码只需要声明注解，不用在每个接口手写重复提交判断。
- 可能的延伸追问：AOP 是基于 JDK 动态代理还是 CGLIB？同类内部方法调用会不会触发 AOP？幂等 key 怎么设计？

- 问题：除了框架本身，你项目里有哪些设计模式？

## 15. Redisson 在项目中解决了什么问题？

## 16. ShardingSphere 在项目中做了什么？

- 问题：为什么订单和支付要分库分表？
- 为什么会问到这个问题：数据库扩展是 Java 中高级面试常问点，项目里有真实配置。
- 对应项目中的哪个部分：`order-service/src/main/resources/shardingsphere-config.yaml`、`pay-service/src/main/resources/shardingsphere-config.yaml`。
- 回答思路：订单服务配置了两个数据源，订单主表、订单项表、订单乘车人关系表做分片，`t_order` 和 `t_order_item` 主要按 `user_id`、`order_sn` 复合分片，乘客关系按 `id_card` 分片；支付服务的 `t_pay` 按 `order_sn`、`pay_sn` 分片。这样可以降低单库单表压力，也方便按订单号、用户维度查询。订单项敏感字段还配置了 AES 加密。
- 可能的延伸追问：分片键为什么这样选？跨分片查询有什么问题？分库分表后分页和事务怎么处理？

# 四、业务流程相关问题

## 18. 查票接口的执行流程是什么？

- 问题：用户查询车票时，后端怎么返回车次、席别、价格和余票？
- 为什么会问到这个问题：查票是 12306 项目的入口，也是缓存设计的核心场景。
- 对应项目中的哪个部分：`TicketController.pageListTicketQuery`、`TicketServiceImpl.pageListTicketQueryV1`、`pageListTicketQueryV2`、`SeatMarginCacheLoader`。
- 回答思路：接口先通过责任链校验参数；再查 Redis 中的站点到地区映射；根据出发地区和到达地区找到经过的车次；拿车次信息、发到站、时长、售卖状态；再查车次站点价格和 `TRAIN_STATION_REMAINING_TICKET` 余票哈希，封装成 `TicketPageQueryRespDTO`。V2 的优化重点是用 pipeline 批量取价格和余票，减少循环中的 Redis 网络请求。需要注意当前 Controller 默认调用的是 V1，V2 方法在 Service 中作为优化版本存在。
- 可能的延伸追问：为什么查票不能直接查数据库？如何保证查票余票准确？V1 的性能瓶颈在哪里？

## 19. 购票接口的执行流程是什么？

- 问题：用户点击购买后，后端发生了什么？
- 为什么会问到这个问题：购票是项目最核心的业务流程，几乎一定会被问。
- 对应项目中的哪个部分：`TicketController.purchaseTicketsV2`、`TicketServiceImpl.purchaseTicketsV2`、`executePurchaseTickets`、`TrainSeatTypeSelector`。
- 回答思路：购票先走责任链校验参数、余票、重复购买等；然后按座位类型分组，为每个席别加本地锁和 Redisson 公平锁；锁内执行选座逻辑；选座完成后保存车票记录，状态为未支付；组装订单创建 DTO，通过 Feign 调订单服务创建订单；最后返回订单号和乘车人座位详情。
- 可能的延伸追问：为什么要按座位类型分组？本地锁和分布式锁都用是否重复？远程创建订单失败时怎么办？

## 20. 座位是怎么分配的？

- 问题：购票时系统怎么给乘客分配座位？
- 为什么会问到这个问题：选座逻辑比普通库存扣减更贴近 12306 业务，容易成为项目亮点。
- 对应项目中的哪个部分：`TrainSeatTypeSelector`、`TrainBusinessClassPurchaseTicketHandler`、`TrainFirstClassPurchaseTicketHandler`、`TrainSecondClassPurchaseTicketHandler`、`AbstractTrainPurchaseTicketTemplate`、`SeatServiceImpl`。
- 回答思路：`TrainSeatTypeSelector` 按座位类型对乘客分组，如果有多个座位类型就用线程池并行处理。然后根据“列车类型 + 座位类型”拼出策略 key，通过策略模式选择对应选座 handler。选座结果会补充乘客真实信息和票价，最后调用座位服务锁定座位。抽象模板里还会根据区间路线扣减 Redis 余票。
- 可能的延伸追问：如果用户指定连座怎么处理？不同车型座位布局不同怎么办？选座失败如何回滚？

## 21. 订单是怎么创建和流转的？

- 问题：订单服务承担哪些状态变化？
- 为什么会问到这个问题：订单状态机是业务系统常见考点。
- 对应项目中的哪个部分：`OrderServiceImpl.createTicketOrder`、`closeTickOrder`、`cancelTickOrder`、`statusReversal`、`OrderStatusEnum`。
- 回答思路：订单创建时生成订单号，写订单主表、订单项、订单乘车人关系表，初始状态是待支付。订单创建成功后发送延迟关闭订单消息。未支付超时会从待支付变成关闭。支付成功后，订单服务消费支付结果消息，把订单和订单项改为已支付，并记录支付时间和支付方式。退款后还有部分退款、全额退款等状态。
- 可能的延伸追问：订单状态可以随便更新吗？如何防止重复关闭？订单号怎么生成？

## 22. 支付回调是怎么处理的？

- 问题：支付宝支付成功后，系统怎么知道订单支付成功？
- 为什么会问到这个问题：支付是典型异步回调场景，面试官会关注幂等和状态一致性。
- 对应项目中的哪个部分：`PayController.pay`、`PayCallbackController.callbackAlipay`、`PayServiceImpl.callbackPay`、`PayResultCallbackOrderSendProduce`。
- 回答思路：创建支付单时，支付服务根据支付渠道和交易类型选择支付宝 Native 策略，插入 `t_pay`。支付宝回调接口收到参数后转成回调请求，再通过策略 handler 校验和处理。支付服务更新支付单状态，如果是支付成功，就发送支付结果 MQ。订单服务消费后更新订单状态，车票服务消费后更新座位为已售。
- 可能的延伸追问：支付宝回调重复通知怎么办？如何验证回调是真的支付宝发来的？支付成功但 MQ 发送失败怎么办？

## 23. 超时未支付订单如何释放库存？

- 问题：用户下单后不支付，座位会一直占着吗？
- 为什么会问到这个问题：这是购票系统里的高频业务问题，也是 MQ 延迟消息的典型落点。
- 对应项目中的哪个部分：`DelayCloseOrderSendProduce`、`DelayCloseOrderConsumer`、`OrderServiceImpl.closeTickOrder`、`seatService.unlock`、`TicketAvailabilityTokenBucket.rollbackInBucket`。
- 回答思路：订单创建时发送 RocketMQ 延迟消息，延迟级别 14，对应 10 分钟。消息到期后车票服务消费，远程调用订单服务关闭订单。如果订单已支付，关闭失败并直接返回；如果订单仍待支付，就释放数据库座位，回滚 Redis 区间余票，并回滚令牌桶。
- 可能的延伸追问：为什么由车票服务消费延迟关闭消息？如果关闭订单成功但释放座位失败怎么办？延迟消息时间如何设定？

# 五、并发与一致性相关问题

## 24. 项目如何防止超卖？

- 问题：多个用户同时买同一车次同一席别，怎么保证不超卖？
- 为什么会问到这个问题：这是 12306 项目最容易被追问的高频问题。
- 对应项目中的哪个部分：`TicketServiceImpl.purchaseTicketsV2`、`AbstractTrainPurchaseTicketTemplate.executeResp`、`SeatServiceImpl.lockSeat`、`TRAIN_STATION_REMAINING_TICKET` 缓存。
- 回答思路：项目不是简单扣一个库存数字，而是先责任链校验余票，再按车次和席别加锁控制并发，锁内执行选座和座位锁定。选座成功后更新数据库座位状态，并扣减经过区间的 Redis 余票。订单超时或取消时会释放座位并回滚缓存。可以补充项目中保留了令牌桶 Lua 脚本方案，但当前购票 V2 的取令牌逻辑被注释，主链路更明确的是锁和座位状态控制。
- 可能的延伸追问：只靠 Redis 扣库存可以吗？数据库座位状态更新如何保证并发安全？锁粒度太粗怎么办？

## 25. 购票 V1 和 V2 的锁设计有什么区别？

- 问题：为什么购票接口有 V1 和 V2？
- 为什么会问到这个问题：版本对比能看出你是否理解性能优化的动机。
- 对应项目中的哪个部分：`TicketServiceImpl.purchaseTicketsV1`、`purchaseTicketsV2`。
- 回答思路：V1 按车次加 Redisson 分布式锁，简单但粒度粗，同一车次不同席别也会互相阻塞。V2 按座位类型分组，锁 key 变成车次加席别，同时使用本地 `ReentrantLock` 和 Redisson 公平锁。这样能减少不同席别之间的锁竞争，也让锁更贴近业务资源。
- 可能的延伸追问：本地锁在多实例下有什么作用？为什么还要分布式锁？公平锁会不会降低吞吐？

## 26. 幂等在项目中怎么落地？

- 问题：如何防止重复提交订单、重复支付、重复消费消息？
- 为什么会问到这个问题：幂等是支付、订单、MQ 场景必问问题。
- 对应项目中的哪个部分：`frameworks/idempotent`、`PassengerController`、`PayServiceImpl.commonPay`、`TicketServiceImpl.purchaseTicketsV1/V2`、各 MQ Consumer 的 `@Idempotent`。
- 回答思路：项目封装了 `@Idempotent` 注解，支持 RESTAPI 和 MQ 场景。乘车人新增修改、购票、创建支付单这些接口使用 SpEL 生成唯一 key；MQ 消费使用消息 key 和 hashCode 组合做幂等 key，避免重复消费导致订单状态或座位状态被重复更新。切面中如果发现重复消费，会根据处理状态决定返回或抛异常。
- 可能的延伸追问：幂等 key 过期时间怎么设置？如果第一次执行失败，幂等 key 怎么处理？接口幂等和 MQ 幂等有什么区别？

## 27. 项目如何处理跨服务一致性？

- 问题：车票、订单、支付分属不同服务，怎么保证一致？
- 为什么会问到这个问题：这是微服务项目核心问题，面试官一般不会只听“加事务”。
- 对应项目中的哪个部分：`TicketServiceImpl.executePurchaseTickets`、`OrderServiceImpl.createTicketOrder`、`DelayCloseOrderConsumer`、`PayServiceImpl.callbackPay`。
- 回答思路：项目没有把跨服务操作放进一个强一致分布式事务，而是通过本地事务加消息和补偿实现最终一致。车票服务锁座后调用订单服务创建订单；订单创建后用延迟消息处理未支付释放；支付成功后用 MQ 驱动订单和座位状态更新。失败场景依赖事务回滚、延迟关闭、取消回滚和幂等消费兜底。
- 可能的延伸追问：如果订单创建成功但车票服务返回失败怎么办？如果支付服务发 MQ 失败怎么办？你会不会引入 Seata？

## 28. 缓存和数据库的一致性怎么保证？

- 问题：余票缓存扣减后，数据库座位状态和 Redis 不一致怎么办？
- 为什么会问到这个问题：缓存一致性是高频中间件问题，项目里有真实实现和预留方案。
- 对应项目中的哪个部分：`AbstractTrainPurchaseTicketTemplate`、`DelayCloseOrderConsumer`、`TicketAvailabilityCacheUpdateHandler`、`CanalCommonSyncBinlogConsumer`。
- 回答思路：主流程里选座成功会扣减经过区间的 Redis 余票，取消或超时关闭会回滚缓存。项目还保留了 Canal binlog 同步方案：消费 `t_seat` 的 UPDATE 事件，根据座位状态变化增减对应区间席别的 Redis 余票。回答时要说明当前代码通过配置 `ticket.availability.cache-update.type` 判断是否走 binlog 模式。
- 可能的延伸追问：先更新数据库还是先更新缓存？Canal 同步有延迟怎么办？缓存重建怎么做？

## 29. MQ 消息重复消费和顺序问题怎么考虑？

- 问题：支付结果消息如果重复消费或乱序，系统会怎样？
- 为什么会问到这个问题：真实系统中 MQ 至少一次投递很常见，面试官会看你是否理解消息语义。
- 对应项目中的哪个部分：`PayResultCallbackOrderConsumer`、`PayResultCallbackTicketConsumer`、`DelayCloseOrderConsumer`、`IdempotentAspect`。
- 回答思路：重复消费主要靠 `@Idempotent` 控制。状态更新时也要结合订单当前状态判断，比如关闭订单只允许待支付状态关闭。顺序方面，项目主要通过状态机约束和幂等减少重复影响。支付成功和延迟关闭可能同时到达时，关闭订单会先查询订单状态，如果已支付则不释放座位。
- 可能的延伸追问：RocketMQ 如何保证局部顺序？如果先收到关闭消息后收到支付成功消息怎么办？消费者异常重试会不会重复扣库存？

## 40. 如果要提高订单和支付的一致性，你会怎么设计？

- 问题：当前最终一致方案还能怎么增强？
- 为什么会问到这个问题：面试官想看你是否能从项目走向系统设计。
- 对应项目中的哪个部分：`OrderServiceImpl.createTicketOrder`、`PayServiceImpl.callbackPay`、MQ produce/consumer。
- 回答思路：可以引入本地消息表或事务消息，保证本地状态变更和消息发送一致；为支付回调和订单状态更新增加更严格的状态机校验；消费者侧做好幂等和失败重试；定时任务扫描异常状态订单做补偿，比如支付成功但订单未更新、订单关闭但座位未释放。
- 可能的延伸追问：RocketMQ 事务消息怎么用？本地消息表怎么设计？补偿任务如何避免重复补偿？

## 41. 如果要做聚合服务或 BFF，你会怎么处理？

- 问题：前端需要一次拿到复杂页面数据时怎么办？
- 为什么会问到这个问题：项目里网关配置出现 aggregation 模式，容易被追问。
- 对应项目中的哪个部分：`gateway-service/application-aggregation.yaml`、`services/pom.xml` 中被注释的 `aggregation-service`。
- 回答思路：当前源码里 aggregation 服务未启用，推测曾考虑聚合层。真正要做时，可以增加聚合服务负责面向页面的组合查询，比如订单详情页同时查订单、支付、车票信息。聚合服务不承载核心状态变更，只做编排和数据组装，避免把业务规则分散到多个地方。
- 可能的延伸追问：聚合服务和网关职责怎么区分？聚合服务调用多个服务失败怎么办？会不会导致链路变长？

## 42. 这个项目你会优先改进哪里？

- 问题：如果继续完善项目，你下一步做什么？
- 为什么会问到这个问题：面试官想看你能否客观看待项目，而不是只讲优点。
- 对应项目中的哪个部分：整体工程、退款流程、消息可靠性、测试、配置安全。
- 回答思路：优先完善三类：第一，可靠性，增加本地消息表或事务消息、补偿任务和更清晰的订单状态机；第二，工程质量，补充核心链路测试和压测脚本，清理包名和配置历史遗留；第三，安全和配置，支付宝密钥、数据库密码等改为配置中心或环境变量管理，敏感配置不直接写在仓库里。表达时不要否定项目，而是说这是学习型项目走向生产化需要补的部分。
- 可能的延伸追问：你会怎么设计压测？哪些指标最关键？你如何证明优化有效？
