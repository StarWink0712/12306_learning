# 项目定位

这个项目可以在面试里定位成：一个模拟铁路 12306 核心购票链路的 Java 微服务项目。

我介绍时不要把它说成普通的后台管理系统，而是要强调它围绕“用户登录、乘车人管理、车票查询、选座购票、订单创建、支付回调、超时关闭、退票退款”这一整条业务链路展开。项目的重点不是页面展示，而是后端如何承接高并发查询和购票场景下的库存、订单、支付、缓存、锁、消息一致性问题。

从源码看，它是 Maven 多模块工程，根模块下分为 `services` 和 `frameworks`。业务服务包括网关、用户、车票、订单、支付；公共能力被拆到缓存、幂等、数据库、Web 统一返回、设计模式、分布式 ID、用户上下文等 starter 模块里。

需要注意的表达边界：源码里部分依赖、包名、注释仍保留 `index12306`、`org.opengoofy`、`nageoffer` 等痕迹，推测这个项目是基于 12306 开源/学习项目进行二次实现和整理。面试时建议说“我基于 12306 购票场景做了微服务化后端实现和源码级学习整理”，不要夸成完全从零原创一整套商业系统。

# 项目背景

这个项目的业务背景是：铁路购票系统的核心难点不是简单下单，而是“查询流量大、购票瞬时并发高、库存不能超卖、订单状态要可靠流转、支付结果异步回调、未支付订单要自动释放座位”。

在这个项目里，车票服务负责查询和购票主流程，订单服务负责订单主表和订单项，支付服务对接支付宝沙箱并处理支付回调，用户服务负责登录、注册、乘车人维护，网关负责鉴权和路由。

从代码看，项目在 `services/ticket-service` 里实现了车票查询 V1/V2、购票 V1/V2、座位选择、余票缓存、取消订单回滚；在 `services/order-service` 里实现了订单创建、订单分页、订单关闭、订单状态反转；在 `services/pay-service` 里实现了支付单创建、支付宝回调、退款；在 `services/user-service` 里实现了用户登录注册和乘车人管理。

# 核心业务目标

我理解这个项目的核心目标是：让用户能完成一条完整的购票闭环，并且在高并发场景下尽量保证系统可用和数据一致。

具体来说包括：

- 用户可以注册、登录，登录后通过 JWT 和网关传递用户上下文。
- 用户可以维护乘车人，购票时根据乘车人 ID 查询真实乘车人信息。
- 用户可以按出发地、目的地、出发站、到达站、日期查询可购买车次、席别、价格和余票。
- 用户可以提交购票请求，系统按车次、席别、乘车人完成座位分配和座位锁定。
- 购票成功后创建订单和订单项，订单初始状态为待支付。
- 订单创建后发送 RocketMQ 延迟消息，超时未支付时关闭订单并释放座位和缓存余票。
- 支付成功后由支付宝回调支付服务，再通过 MQ 通知订单服务改状态、通知车票服务把座位从锁定改为已售。
- 取消订单或退款时，走订单、支付、车票之间的协作，完成状态变更和资源回滚。

# 主要业务流程

面试时我可以按“查票、购票、下单、支付、关闭”这条链路讲。

第一步是登录和用户上下文。用户调用用户服务登录接口，`UserLoginServiceImpl` 支持用户名、手机号、邮箱登录，校验成功后生成 JWT，并把登录信息放到 Redis，默认缓存 30 分钟。网关里的 `TokenValidateGatewayFilterFactory` 会对需要登录的路径做 Token 校验，解析出用户 ID、用户名、真实姓名，写到请求头。下游服务通过 `UserTransmitFilter` 把这些请求头放进 `UserContext`，业务代码里就可以直接拿当前用户。

第二步是车票查询。用户调用 `/api/ticket-service/ticket/query`，进入 `TicketServiceImpl.pageListTicketQueryV1`。代码里先走查询责任链，校验参数和站点合法性，然后从 Redis 里查站点到地区的映射、地区到车次的映射、车次站点价格、区间余票。V1 版本是逐车次、逐席别查询 Redis，代码注释里也指出它存在网络交互次数多的问题；V2 版本 `pageListTicketQueryV2` 用 Redis pipeline 批量取价格和余票，主要是减少 Redis 往返次数。

第三步是购票。用户调用 `/api/ticket-service/ticket/purchase/v2`，先经过购票责任链，校验必填参数、业务合法性、重复购买、余票等。然后按照座位类型分组，为每种席别构造锁：本地用 Caffeine 缓存 `ReentrantLock`，分布式用 Redisson 公平锁，锁粒度从“整车次”细化到“车次 + 座位类型”。拿到锁之后，调用 `executePurchaseTickets`。

第四步是选座和锁座。`TrainSeatTypeSelector` 会按座位类型分组，如果一次买多种席别，会用线程池并行处理。具体座位分配通过策略模式选择，比如高铁商务座、一等座、二等座分别有对应 handler。选座后远程调用用户服务查询乘车人真实信息，再查询价格，最后调用 `seatService.lockSeat` 锁定座位。

第五步是创建订单。车票服务会先保存 `t_ticket` 记录，状态是未支付，然后通过 OpenFeign 调用订单服务的 `/api/order-service/order/ticket/create`。订单服务生成订单号，写入 `t_order`、`t_order_item`、`t_order_item_passenger`，订单状态是待支付，并发送 RocketMQ 延迟关闭订单消息，延迟级别 14，对应 10 分钟。

第六步是支付和回调。支付服务创建支付单时会走支付策略，当前代码里主要是支付宝 Native 支付，支付单写入 `t_pay`。支付宝回调 `/api/pay-service/callback/alipay` 后，支付服务更新支付单状态，并发送支付结果 MQ。订单服务消费支付结果后把订单和订单项改为已支付；车票服务消费同一支付结果后，把座位状态改为已售。

第七步是超时关闭和取消回滚。如果用户 10 分钟未支付，车票服务的 `DelayCloseOrderConsumer` 消费延迟消息，远程调用订单服务关闭订单。如果订单确实还是待支付，就释放数据库座位、回滚 Redis 余票缓存，并回滚令牌桶。用户主动取消订单时，`cancelTicketOrder` 也是类似思路。

# 系统模块划分

`gateway-service`：API 网关，端口配置为 9000。负责服务路由和登录态校验。`application-dev.yaml` 里直接路由到 user、ticket、pay、order；`application-aggregation.yaml` 里路由到 aggregation 服务，但 `services/pom.xml` 中 aggregation-service 被注释掉了，所以当前项目实际启用的是五个服务模块。这里可以说：推测项目曾考虑过聚合服务模式，但当前源码主线是直接微服务路由。

`user-service`：用户服务。负责用户注册、登录、注销、用户信息查询、乘车人增删改查。注册用了责任链、Redis/Redisson 锁、布隆过滤器和用户名复用分片集合；登录生成 JWT，乘车人列表用 Redis 缓存。

`ticket-service`：车票服务，是最核心的业务服务。负责站点/车次查询、余票查询、购票、选座、锁座、取消订单回滚、退票发起、余票缓存初始化、Canal binlog 同步余票缓存等。

`order-service`：订单服务。负责订单创建、订单详情查询、订单分页、本人订单查询、订单关闭、订单状态反转。订单主表、订单项、订单乘车人关系表使用 ShardingSphere 分库分表。

`pay-service`：支付服务。负责支付单创建、支付宝回调、支付单查询、退款。支付记录表 `t_pay` 使用 ShardingSphere 分库分表，支付结果通过 RocketMQ 通知订单和车票服务。

`frameworks` 公共模块：包括 `base`、`cache`、`convention`、`database`、`designpattern`、`distributedid`、`idempotent`、`log`、`web`、`bizs/user`。这些模块不是业务接口，而是把公共能力抽出来，比如统一返回、全局异常、Redis 缓存封装、幂等注解、责任链、策略模式、用户上下文传递、分布式 ID 等。

# 技术栈

项目基础技术栈是 Java 17、Spring Boot 3.5.7、Maven 多模块。

微服务相关：Spring Cloud、Spring Cloud Alibaba、Nacos 服务发现/配置、Spring Cloud Gateway、OpenFeign、Spring Cloud LoadBalancer、OkHttp。

数据访问相关：MySQL、MyBatis-Plus、MyBatis XML、ShardingSphere-JDBC。订单服务和支付服务使用 ShardingSphere 做分库分表，订单服务还配置了身份证号和手机号 AES 加密。

缓存和并发相关：Redis、StringRedisTemplate、Redisson、Caffeine、Lua 脚本、布隆过滤器、Redis pipeline。

消息和异步相关：RocketMQ，用于订单延迟关闭、支付结果回调、退款结果回调、Canal binlog 同步事件消费。

治理和监控相关：Sentinel、Spring Boot Actuator、Micrometer Prometheus、XXL-Job、Hippo4j 动态线程池。

业务集成和工具：支付宝 SDK、JWT、Fastjson/Fastjson2、Hutool、Lombok、Crane4j。

# 关键实现点

第一个关键点是网关鉴权和用户上下文透传。网关解析 JWT 后把用户信息写入请求头，下游通过 `UserTransmitFilter` 放入 `UserContext`。这样订单、购票、乘车人等接口不用反复解析 Token，而是统一从上下文拿当前用户。

第二个关键点是查询性能优化。车票查询涉及车站映射、车次、站点关系、价格、余票多个维度。项目里把车站映射、地区车次映射、车次价格、区间余票放到 Redis。V1 查询会在循环里多次访问 Redis，V2 用 pipeline 批量获取，面试时可以说我的理解是“这不是换了个缓存组件，而是减少了网络往返次数，把热点查询从多次串行 IO 优化成批量 IO”。

第三个关键点是购票并发控制。购票 V1 是按车次加分布式锁，粒度比较粗。购票 V2 按座位类型分组，锁粒度变成车次加席别，并且组合了本地锁和 Redisson 公平锁，减少不同席别之间的阻塞。这里体现的是业务锁粒度设计，而不是单纯加锁。

第四个关键点是座位分配策略。`TrainSeatTypeSelector` 先按席别分组，再根据“列车类型 + 座位类型”走策略模式选择不同选座 handler。这样不同车型、不同席别的选座规则可以隔离，不会把所有规则写成一个巨大的 if-else。

第五个关键点是订单超时关闭。订单创建后立即投递 RocketMQ 延迟消息。延迟消息到期后，车票服务调用订单服务关闭订单，如果订单仍是待支付，就释放座位、回滚 Redis 余票、回滚令牌桶。这个流程解决的是“用户占座但不支付”导致库存长期不可用的问题。

第六个关键点是支付结果异步驱动状态流转。支付服务不直接强耦合修改订单和座位，而是收到支付宝回调后发 MQ。订单服务消费后改订单状态，车票服务消费后改座位状态。这样支付、订单、车票之间是事件协作关系。

第七个关键点是幂等。项目有独立的 `idempotent` starter，通过 `@Idempotent` 支持 REST API 和 MQ 场景。代码里用户乘车人修改、支付创建、购票、MQ 消费等地方都使用了幂等注解，避免重复提交或重复消费造成状态重复变更。

第八个关键点是分库分表和数据安全。订单库配置了两个数据源、每个表 32 张分片表，`t_order`、`t_order_item` 按 `user_id`、`order_sn` 分片；`t_order_item_passenger` 按 `id_card` 分片。支付表 `t_pay` 按 `order_sn`、`pay_sn` 分片。订单项里的身份证和手机号配置了 ShardingSphere AES 加密。

第九个关键点是余票缓存一致性。项目有两种思路：一种是在业务流程里直接扣减或回滚 Redis 余票；另一种是通过 Canal binlog 事件同步 `t_seat` 变化来更新余票缓存。需要精确表达的是：`TicketAvailabilityTokenBucket` 和 Canal 同步代码都存在，但购票 V2 中获取令牌的代码目前被注释了，所以面试时可以说“项目保留了令牌桶和 binlog 同步方案，当前主链路更明显的是锁 + 选座 + Redis 余票扣减 + 关闭订单回滚”。

# 项目中能体现出的工程能力

这个项目能体现的不是“用了多少技术”，而是我对复杂业务链路的拆解能力。

第一，能按业务边界拆微服务。用户、车票、订单、支付、网关边界比较清楚，车票服务负责库存和座位，订单服务负责订单状态，支付服务负责支付渠道和回调。

第二，能理解高并发购票里的核心矛盾。查票是读多场景，要靠缓存和批量查询降低数据库压力；购票是写冲突场景，要靠锁粒度、幂等、库存扣减、超时释放来防止超卖和重复占座。

第三，能把公共能力抽象成工程组件。缓存、幂等、统一异常、统一返回、用户上下文、责任链、策略模式、分布式 ID 都被放进 `frameworks`，这说明项目不是所有业务都堆在 Controller/Service 里。

第四，能处理异步状态流转。订单创建、支付成功、座位售出、订单超时关闭不是一个同步方法直接干完，而是通过 RocketMQ 把服务间状态变化串起来。

第五，能关注数据规模和敏感信息。订单和支付做了 ShardingSphere 分片，订单乘车人敏感字段做了加密，MyBatis-Plus 配置了逻辑删除。

第六，能识别项目边界和不足。比如部分配置还保留 aggregation 路由但模块未启用，部分包名/依赖命名混用 `com.guoxu` 和 `org.opengoofy`，部分退款返回值还是 `null/TODO`。面试时如果被问到，我会诚实说这是学习型项目中待完善的地方，而不是回避。

# 面试时如何介绍这个项目

可以用这段作为 1 分钟版本：

这个项目是一个模拟 12306 核心购票链路的 Java 微服务项目。我主要围绕用户、车票、订单、支付、网关几个服务理解和整理了完整业务闭环：用户登录后通过网关鉴权，查询车票时走 Redis 缓存和责任链校验，购票时按车次和席别做并发控制并完成选座锁座，然后远程调用订单服务创建待支付订单。订单创建后会发送 RocketMQ 延迟消息，如果用户超时未支付，系统会关闭订单并释放座位和余票缓存。支付成功后，支付服务通过支付宝回调更新支付单，再通过 MQ 通知订单服务更新订单状态、通知车票服务把座位改成已售。

如果面试官让我展开，我会重点讲三块：

第一块是查票性能。项目里车站映射、车次关系、价格和区间余票都做了 Redis 缓存，V2 查询用 pipeline 批量取数据，核心收益是减少 Redis 网络交互。

第二块是购票并发。购票不是简单扣库存，而是先责任链校验，再按席别分组，用本地锁加 Redisson 分布式锁控制并发，之后通过策略模式选座、锁座、创建订单，并用幂等注解防重复提交。

第三块是订单和支付的一致性。订单创建后靠 RocketMQ 延迟消息解决未支付占座问题；支付成功后靠 MQ 异步驱动订单状态和座位状态更新，避免支付服务直接强依赖多个业务服务。

最后我会补一句边界：这个项目是学习和面试准备性质的 12306 后端实现，源码里也能看到一些后续可优化点，比如 aggregation 服务未启用、退款返回值还不完整、包名有历史遗留。我的重点不是说它已经是生产级 12306，而是通过它说明我理解复杂购票系统里查询、库存、订单、支付、缓存和消息协作这些核心问题。
