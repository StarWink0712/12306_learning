# 面试准备：缓存与性能模块

## 模块定位

缓存与性能主要围绕两个高频场景：

- 查票是高频读，需要减少数据库压力和 Redis 往返。
- 购票是高并发写，需要用缓存做前置余票校验，但不能只依赖缓存保证最终一致。

项目里的缓存能力分两层：业务服务直接设计 key，公共 `frameworks/cache` 提供安全加载和 Redis 封装。

## Redis 使用场景

用户服务：

- 登录态缓存：登录成功后把 `accessToken -> UserLoginRespDTO` 放 Redis，默认 30 分钟。
- 乘车人列表缓存：`USER_PASSENGER_LIST`。
- 用户名复用集合：`USER_REGISTER_REUSE_SHARDING`。
- 注册布隆过滤器：减少用户名查询穿透。

车票服务：

- `TRAIN_INFO`：车次基础信息。
- `REGION_TRAIN_STATION_MAPPING`：地区和站点映射。
- `REGION_TRAIN_STATION`：地区之间可达车次。
- `TRAIN_STATION_PRICE`：车次区间价格。
- `TRAIN_STATION_REMAINING_TICKET`：区间余票 Hash。
- `TRAIN_CARRIAGE`、`TRAIN_CARRIAGE_SEAT_STATUS`：车厢和座位状态相关缓存。
- `TICKET_AVAILABILITY_TOKEN_BUCKET`：令牌桶。

支付服务：

- `ORDER_PAY_RESULT_INFO`：订单支付结果缓存。

公共能力：

- 幂等 key。
- Redisson 分布式锁。
- `safeGet` 防缓存击穿。

## 查票性能优化

查票在 `TicketServiceImpl.pageListTicketQueryV1/pageListTicketQueryV2`。

V1 的问题：

- 在循环中逐个读取价格和余票。
- 车次多、席别多时 Redis 网络往返次数明显增加。

V2 的优化：

- 批量构造 Redis key。
- 使用 pipeline 一次性读取多个价格和余票。
- 主要收益是减少客户端到 Redis 的网络交互。

面试里可以补一句：pipeline 减少的是网络往返，不代表 Redis 命令数量消失，所以后续仍要关注 Redis 热点、Java 侧组装、JSON 反序列化和返回数据量。

## 缓存 key 设计

项目的 key 设计按数据变化频率拆分：

- 车次、站点、价格相对稳定，可以长缓存或预热。
- 余票变化频繁，单独用 `TRAIN_STATION_REMAINING_TICKET` 维护。
- 区间余票 key 后缀是 `trainId_startStation_endStation`。
- 席别作为 Redis Hash field，方便单独增减某个席别库存。

这样避免每次余票变化都重写整段车次信息。

## safeGet 防击穿

公共缓存核心在 `StringRedisTemplateProxy.safeGet`：

- 先查缓存。
- 缓存命中直接返回。
- 未命中时，如果布隆过滤器判断 key 不存在，可以快速返回，防穿透。
- 获取 Redisson 分布式锁。
- 拿到锁后二次检查缓存。
- 仍未命中才调用 `CacheLoader` 查库并写缓存。

这套逻辑适合回答缓存击穿、穿透和双重检查锁。

## 缓存一致性

项目里有两种余票缓存更新思路。

业务内更新：

- 购票成功后直接扣减 Redis 区间余票。
- 订单取消或超时关闭后回滚 Redis 区间余票。

binlog 同步：

- `CanalCommonSyncBinlogConsumer` 消费 binlog 事件。
- `TicketAvailabilityCacheUpdateHandler` 根据座位变化更新余票缓存。

稳妥表达是：当前主链路里能直接看到业务内扣减和回滚，同时保留 Canal 异步校准方案。生产化还要加对账和补偿。

## 缓存预热

车票服务有 XXL-Job 相关任务：

- `TrainStationJobHandler`
- `TrainStationDetailJobHandler`
- `TrainStationRemainingTicketJobHandler`
- `RegionTrainStationJobHandler`

它们适合预热站点、车次和余票基础数据。

面试里可以说明：生产环境不能随便全量刷新实时余票缓存，应该分批、灰度、版本化 key 或结合 binlog 校准，避免覆盖实时变化。

## 本地缓存

项目里使用 Caffeine：

- `localLockMap` 缓存车次席别对应的 `ReentrantLock`，1 天过期。
- `tokenTicketsRefreshMap` 缓存令牌桶刷新标记，10 分钟过期。

本地缓存适合进程内热点数据或对象复用，但不能用来做跨实例一致性判断。

## 面试高频问题

- 问题：Redis 在项目中用来做什么？
- 回答：登录态、乘车人列表、车次站点价格、区间余票、支付结果、幂等 key、布隆过滤器和分布式锁都用到了 Redis。

- 问题：查票 V2 为什么更快？
- 回答：V2 用 pipeline 批量读取价格和余票，减少 Redis 网络往返。它不是减少业务复杂度，而是减少大量循环读 Redis 的 IO 开销。

- 问题：如何防缓存击穿？
- 回答：公共 `safeGet` 先查缓存，未命中后加 Redisson 锁，拿锁后二次检查，最后才查库写缓存。

- 问题：余票缓存不一致怎么办？
- 回答：购票扣减、取消和关闭回滚，保留 Canal binlog 同步做异步校准。生产上再加定时对账和异常补偿。

## 可改进点

- 查票默认入口可以切到 V2 并做压测。
- 热门线路可以加本地缓存、请求合并或结果预聚合。
- 对 `TRAIN_STATION_REMAINING_TICKET` 这类热点 key 要监控 Redis QPS 和大 key 风险。
- `safeGet` 可增加锁等待超时、降级和缓存加载耗时监控。

## 一句话总结

缓存与性能模块可以概括为：查票用拆分缓存和 pipeline 提升读性能，购票用余票缓存做前置判断，但最终一致还要靠座位状态、回滚和补偿。
