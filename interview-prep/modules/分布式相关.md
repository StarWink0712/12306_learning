# 面试准备：分布式相关模块

## 模块定位

这个项目是 Maven 多模块微服务结构，业务服务主要包括：

- `gateway-service`：路由和鉴权。
- `user-service`：用户、登录、乘车人。
- `ticket-service`：查票、购票、选座、座位和余票。
- `order-service`：订单创建、查询、关闭、状态流转。
- `pay-service`：支付单、支付宝回调、退款。

公共能力放在 `frameworks`，比如缓存、幂等、统一异常、用户上下文、分布式 ID、责任链和策略模式。

## 服务协作

同步调用主要使用 OpenFeign：

- 车票服务调用用户服务查询乘车人真实信息。
- 车票服务调用订单服务创建订单、取消订单、查询订单详情。
- 车票服务调用支付服务查询支付信息和发起退款。
- 支付服务调用订单服务查询订单详情。
- 订单服务调用用户服务查询当前用户真实身份信息。

异步协作主要使用 RocketMQ：

- 订单创建后发送延迟关闭订单消息。
- 支付成功后发送支付结果消息。
- 退款成功后发送退款结果消息。
- Canal binlog 同步也通过 MQ 消费处理。

## 网关和用户上下文

`gateway-service` 通过 `TokenValidateGatewayFilterFactory` 做统一鉴权：

- 判断请求路径是否命中 `blackPathPre`。
- 从 `Authorization` 读取 JWT。
- 解析出用户 ID、用户名、真实姓名。
- 写入请求头传给下游服务。

下游 `UserTransmitFilter` 读取请求头并写入 `UserContext`。`UserContext` 使用 `TransmittableThreadLocal`，请求结束后 finally 清理。

面试里要补充生产边界：下游服务不能完全信任请求头，应该限制只能从网关或内网访问，并做服务间鉴权。

## 跨服务一致性

项目没有把车票、订单、支付放进强一致分布式事务，而是本地事务 + MQ + 补偿的最终一致思路。

典型链路：

- 车票服务选座锁座，保存车票记录。
- 车票服务通过 Feign 调订单服务创建待支付订单。
- 订单服务本地事务写订单表，并发送延迟关闭消息。
- 支付服务收到支付宝回调后更新支付单，并发支付结果 MQ。
- 订单服务消费 MQ 更新订单状态。
- 车票服务消费 MQ 更新座位为已售。
- 超时未支付时，延迟关闭消息触发关闭订单和释放座位。

回答时可以说：这里牺牲了强一致，换取服务解耦和可扩展性，核心是状态可重试、消息幂等、失败可补偿。

## MQ 场景

订单延迟关闭：

- Producer：`DelayCloseOrderSendProduce`。
- Event：`DelayCloseOrderEvent`。
- Consumer：`DelayCloseOrderConsumer`。
- 作用：订单超时未支付后释放座位和余票。

支付结果回调：

- Producer：`PayResultCallbackOrderSendProduce`。
- Consumer：订单服务 `PayResultCallbackOrderConsumer`，车票服务 `PayResultCallbackTicketConsumer`。
- 作用：支付成功后分别更新订单状态和座位状态。

退款结果回调：

- 退款服务创建退款后发消息。
- 订单服务消费后更新退款相关状态。

MQ consumer 上普遍使用 `@Idempotent`，避免重复消费。

## 分布式锁

项目使用 Redisson：

- 用户注册按用户名加锁，避免并发重复注册。
- 购票 V1 按车次加锁。
- 购票 V2 按车次加席别加锁。
- 订单取消按订单号加锁。
- 缓存 `safeGet` 用锁防击穿。
- 令牌桶初始化也有锁。

面试表达重点：锁 key 要和业务资源对应，不能只说“用了分布式锁”。

## 分布式 ID

项目里有公共 `frameworks/distributedid`，也有订单、支付服务自己的 ID 生成器：

- 公共模块提供 Snowflake、workerId 选择等能力。
- `OrderIdGeneratorManager` 用于订单号。
- `PayIdGeneratorManager` 用于支付流水号。
- 启动时会通过 Redis 自增和 Redisson 锁分配节点号。

可以回答：分布式 ID 要兼顾唯一性、趋势递增、业务可定位和分片友好。

## 分库分表

订单和支付服务使用 ShardingSphere：

- 订单主表和订单项按 `user_id, order_sn` 复合分片。
- 订单乘车人关系按 `id_card` 分片。
- 支付表按 `order_sn, pay_sn` 分片。
- 订单项中的身份证和手机号配置 AES 加密。

这体现的是数据规模和查询路径设计，而不是简单为了“用分库分表”。

## 面试高频问题

- 问题：服务为什么这样拆？
- 回答：用户、车票、订单、支付分别有清晰数据归属。车票负责座位和余票，订单负责交易状态，支付负责支付渠道，网关负责统一入口。

- 问题：跨服务一致性怎么保证？
- 回答：不使用一个大事务，而是本地事务、MQ、幂等和补偿。支付成功、订单关闭这类状态变化都通过消息驱动。

- 问题：Feign 调用失败怎么办？
- 回答：当前代码多是记录日志并抛异常，依赖事务回滚和超时关闭兜底。生产上要加超时、熔断、幂等业务号和补偿任务。

- 问题：为什么支付服务不直接改订单和座位？
- 回答：支付服务只维护支付域，订单和座位分别属于订单、车票服务。MQ 解耦后，每个服务处理自己的状态。

## 可改进点

- 关键 MQ 可引入本地消息表或事务消息，增强“本地事务成功 + 消息可靠投递”。
- 增加补偿任务，扫描支付成功但订单未更新、订单超时未关闭、座位长时间锁定等异常。
- Feign 调用增加统一超时、熔断降级和错误码规范。
- 增加 traceId 全链路透传，方便跨服务排查。

## 一句话总结

分布式相关可以概括为：同步 Feign 串起主流程，异步 MQ 驱动状态流转，锁、幂等、分片和补偿共同支撑最终一致。
