# 面试准备：工程与异常处理模块

## 模块定位

工程与异常处理模块主要体现项目的“公共能力沉淀”。

相关 `frameworks` 模块包括：

- `convention`：统一错误码、异常、分页、返回对象。
- `web`：统一响应和全局异常处理。
- `cache`：Redis 缓存封装。
- `idempotent`：接口和 MQ 幂等。
- `designpattern`：责任链、策略模式。
- `database`：MyBatis-Plus、分页、自动填充、ID 生成接入。
- `log`：日志注解和日志打印 DTO。
- `common`：线程池、工具类、通用枚举。
- `bizs/user`：用户上下文传递。

## 统一返回

核心类：

- `Result`
- `Results`
- `BaseErrorCode`

业务接口一般返回 `Result<T>`，成功用 `Results.success`，失败用统一错误码和消息。

面试表达：统一返回不是为了形式统一，而是让前端、网关、监控能按固定结构处理成功、失败和错误码。

## 异常体系

核心类：

- `AbstractException`
- `ClientException`
- `ServiceException`
- `RemoteException`
- `GlobalExceptionHandler`

可以这样区分：

- `ClientException`：客户端参数、重复提交、非法操作等。
- `ServiceException`：业务服务内部状态异常、数据异常。
- `RemoteException`：远程服务调用异常。

`GlobalExceptionHandler` 负责统一捕获异常并转成统一响应。

## 参数校验

项目里很多业务前置校验使用责任链：

- 用户注册责任链。
- 查票责任链。
- 购票责任链。
- 退票责任链。

相关类：

- `AbstractChainContext`
- `AbstractChainHandler`
- 各业务 `*ChainHandler`

面试里可以说：复杂业务校验不要堆在一个 service 方法里，用责任链拆成可排序、可扩展的小步骤。

## 幂等组件

核心类：

- `@Idempotent`
- `IdempotentAspect`
- `IdempotentExecuteHandlerFactory`
- `IdempotentSpELByRestAPIExecuteHandler`
- `IdempotentSpELByMQExecuteHandler`

覆盖场景：

- REST API：购票、支付创建、乘车人修改等。
- MQ：支付结果、退款结果、延迟关闭、Canal 同步等。

MQ 幂等会记录消费中和已消费状态，异常时清理 key 允许重试，成功后标记已消费。

## 日志与排查

项目里有 `@ILog` 和日志 DTO，车票购票等关键方法上可以看到日志注解。

建议面试表达：

- 关键入口记录业务单号、用户、耗时、异常。
- 敏感字段不能原样打印，比如身份证、手机号、token。
- 跨服务排查需要 traceId，目前可以作为后续改进点。

## 数据库公共能力

`frameworks/database` 提供：

- `BaseDo` 基础实体。
- `MybatisPlusAutoConfiguration`。
- `MyMetaObjectHandler` 自动填充。
- `PageUtil` 分页转换。
- `CustomIdGenerator`。

面试时不用展开太久，可以和工程化一起提：业务服务只定义实体和 Mapper，分页、审计字段、统一配置沉淀到公共模块。

## 线程池与动态配置

相关能力：

- `ThreadPoolBuilder`
- `EagerThreadPoolExecutor`
- `TaskQueue`
- 车票服务的 `Hippo4jThreadPoolConfiguration`
- `TrainSeatTypeSelector` 多席别并行选座

面试里可以说：线程池主要用于可并行的选座策略执行，但生产上要关注核心线程、队列长度、拒绝策略和监控。

## 面试高频问题

- 问题：项目如何统一异常和返回？
- 回答：公共 convention 定义错误码、异常和 Result，web 模块用全局异常处理器统一捕获并返回固定结构。

- 问题：责任链用在哪里？
- 回答：用户注册、查票、购票、退票等前置校验。它把参数非空、业务合法性、库存校验、重复购买拆开，避免主流程过长。

- 问题：AOP 用在哪里？
- 回答：幂等组件通过 `@Idempotent` + AOP 拦截 REST API 和 MQ consumer，业务执行前生成幂等 key，成功或异常后做不同处理。

- 问题：线上问题怎么排查？
- 回答：按订单号、用户、车次、消息 key 串日志；看 MQ 重试和堆积、Redis 余票、数据库订单和座位状态；后续应补 traceId 和指标监控。

## 需要谨慎表达

- 当前项目存在 `com.guoxu` 与 `org.opengoofy/index12306` 包名混用，切面 pointcut、注解包名和自动配置路径要重点确认是否完全匹配。
- 一些配置里有本地数据库密码、支付宝沙箱密钥等，生产要迁移到配置中心或密钥管理系统。
- 统一返回不代表 HTTP 状态码都可以忽略，网关鉴权、参数错误、系统异常仍应合理设置状态码。
- 日志要避免打印身份证、手机号、token、支付回调完整敏感参数。

## 可改进点

- 接入 traceId 全链路透传。
- 增加关键指标：缓存命中率、锁等待、MQ 堆积、Feign 超时、订单关闭失败数。
- 完善 OpenAPI 文档和错误码字典。
- 对幂等、分片算法、订单状态流转补测试。

## 一句话总结

工程与异常处理模块可以概括为：公共 starter 统一响应、异常、缓存、幂等和设计模式，让业务服务更聚焦购票、订单和支付本身。
