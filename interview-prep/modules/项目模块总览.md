# 面试准备：项目模块总览

> 说明：当前项目不是单一模块，而是 Maven 多模块工程。这里按真实代码结构整理：5 个业务服务模块，加上 `frameworks` 下的公共能力模块。

# gateway-service

## 模块职责

- 负责统一入口、路径路由和登录态校验。
- 根据 `/api/user-service/**`、`/api/ticket-service/**`、`/api/order-service/**`、`/api/pay-service/**` 将请求转发到对应服务。
- 对需要登录的路径解析 JWT，并把用户信息放到请求头传给下游服务。

## 主要流程

- 请求进入网关。
- `TokenValidateGatewayFilterFactory` 判断请求路径是否命中黑名单前缀。
- 命中后读取 `Authorization`，用 `JWTUtil.parseJwtToken` 解析用户信息。
- 校验成功后写入 `userId`、`username`、`realName` 请求头。
- Gateway 根据 `application-dev.yaml` 或 `application-aggregation.yaml` 路由到目标服务。

## 涉及的关键类和方法

- `GatewayServiceApplication`：网关启动类。
- `TokenValidateGatewayFilterFactory.apply`：网关鉴权核心逻辑。
- `JWTUtil.parseJwtToken`：解析 Token。
- `application-dev.yaml`：直接路由到 user、ticket、order、pay 服务。
- `application-aggregation.yaml`：路由到 aggregation 服务，但当前 `services/pom.xml` 中 aggregation-service 被注释。

## 面试常见问题

- 问题：为什么鉴权放在网关做？
- 考察点：统一入口、避免下游重复解析 Token。
- 回答思路：网关统一校验登录态，解析用户信息后透传给下游，下游通过用户上下文使用。
- 延伸追问：如果绕过网关直接访问下游怎么办？

- 问题：网关怎么知道哪些接口要登录？
- 考察点：Gateway 过滤器配置。
- 回答思路：`TokenValidate` 过滤器通过 `blackPathPre` 配置需要校验的路径前缀。
- 延伸追问：白名单和黑名单哪种更安全？

## 深入追问

- 主问题：网关只解析 JWT，是否需要查 Redis 登录态？
- 第一层追问：JWT 没过期但用户已注销怎么办？
- 第二层追问：网关如何支持 Token 续期？
- 回答思路：当前项目主要解析 JWT；生产化可以结合 Redis 登录态、Token 黑名单或刷新 Token 机制。

## 设计思路

- 网关只做统一入口、鉴权和路由，不承载具体业务。
- 用户信息通过请求头传递，降低下游重复解析 Token 的成本。

## 未来可改进点

- 增加 Token 黑名单、刷新 Token、统一鉴权异常响应。
- 限制下游服务只能被网关访问。
- 补充网关限流和灰度路由。

## 面试表达建议

可以说：“网关模块主要解决入口统一和登录态校验问题。它不是业务服务，只负责把用户身份解析出来并透传给下游，真正的购票、订单、支付逻辑仍然在各自服务里。”

# user-service

## 模块职责

- 负责用户注册、登录、注销、用户信息查询。
- 负责乘车人增删改查。
- 为车票服务和订单服务提供用户、乘车人真实信息查询能力。

## 主要流程

- 登录：`UserLoginServiceImpl.login` 支持用户名、手机号、邮箱登录，成功后生成 JWT，并把登录信息缓存到 Redis。
- 注册：走责任链校验，再通过 Redisson 按用户名加锁，插入用户主表、手机号表、邮箱表。
- 乘车人管理：新增、修改、删除乘车人，并删除用户乘车人缓存。
- 下游查询：车票服务通过 Feign 调用户服务查询乘车人真实信息。

## 涉及的关键类和方法

- `UserLoginController`：登录、校验登录、退出登录接口。
- `UserInfoController`：注册、查询、注销、修改用户接口。
- `PassengerController`：乘车人接口。
- `UserLoginServiceImpl.login/register/deletion`：登录、注册、注销核心逻辑。
- `PassengerServiceImpl.listPassengerQueryByUsername/listPassengerQueryByIds/savePassenger`：乘车人核心逻辑。
- `RBloomFilterConfiguration`：注册场景布隆过滤器配置。

## 面试常见问题

- 问题：登录态怎么实现？
- 考察点：JWT、Redis、网关透传。
- 回答思路：登录成功后生成 JWT，同时把登录响应放 Redis；网关解析 Token 后传用户信息。
- 延伸追问：注销后 Token 还有效怎么办？

- 问题：注册时如何防止用户名重复？
- 考察点：分布式锁、布隆过滤器、数据库唯一约束。
- 回答思路：先责任链校验，再按用户名加 Redisson 锁，插入数据库时捕获唯一键冲突，同时维护用户名复用集合和布隆过滤器。
- 延伸追问：布隆过滤器误判怎么办？

## 深入追问

- 主问题：乘车人列表为什么要缓存？
- 第一层追问：乘车人更新后缓存怎么处理？
- 第二层追问：缓存删除失败怎么办？
- 回答思路：乘车人列表是购票常用数据，缓存能减少数据库查询；更新后删除缓存，后续查询重新加载。生产化可加重试或延迟双删。

## 设计思路

- 用户服务只维护用户和乘车人数据，不直接参与库存和订单状态。
- 当前用户信息通过 `UserContext` 获取，减少业务层重复传参。

## 未来可改进点

- 密码加密存储，目前不应按明文密码思路长期保留。
- 登录态续期、Token 黑名单、账号风控。
- 完善用户注销后的缓存、Token、历史订单展示策略。

## 面试表达建议

可以说：“用户模块看起来像基础 CRUD，但项目里它和购票链路关系很紧。购票选座后需要根据乘车人 ID 查询真实姓名、身份证、手机号，所以用户服务也承担了购票链路的数据支撑。”

# ticket-service

## 模块职责

- 负责车站、车次、余票查询。
- 负责购票、选座、锁座、取消订单回滚、退票发起。
- 消费订单延迟关闭消息和支付结果消息，维护座位状态和余票缓存。

## 主要流程

- 查票：`TicketController.pageListTicketQuery` 调用 `pageListTicketQueryV1`，V2 中实现 Redis pipeline 优化。
- 购票：`purchaseTicketsV2` 责任链校验后，按席别加本地锁和分布式锁，再执行选座。
- 选座：`TrainSeatTypeSelector` 根据列车类型和席别选择具体策略。
- 建单：`executePurchaseTickets` 保存车票记录后，通过 Feign 调订单服务创建订单。
- 回滚：超时关闭或取消订单时释放座位，回滚 Redis 余票和令牌桶。

## 涉及的关键类和方法

- `TicketController`：查票、购票、取消、支付查询、退票入口。
- `TicketServiceImpl.pageListTicketQueryV1/pageListTicketQueryV2`：查票逻辑。
- `TicketServiceImpl.purchaseTicketsV1/purchaseTicketsV2/executePurchaseTickets`：购票主链路。
- `TrainSeatTypeSelector.select`：选座策略入口。
- `AbstractTrainPurchaseTicketTemplate.executeResp`：选座后扣减区间余票。
- `DelayCloseOrderConsumer`：消费延迟关闭订单消息。
- `PayResultCallbackTicketConsumer`：支付成功后更新座位为已售。
- `TicketAvailabilityTokenBucket`：令牌桶方案。
- `TicketAvailabilityCacheUpdateHandler`：Canal 同步余票缓存方案。

## 面试常见问题

- 问题：查票为什么不用直接查数据库？
- 考察点：高频读、缓存拆分、Redis pipeline。
- 回答思路：查票要组合车次、价格、余票，读流量大，项目把静态数据和余票缓存到 Redis，V2 用 pipeline 减少网络往返。
- 延伸追问：缓存和数据库不一致怎么办？

- 问题：购票如何防止超卖？
- 考察点：责任链、锁、选座、座位状态、余票回滚。
- 回答思路：先校验，再按车次和席别加锁，锁内选座和锁座，订单取消或超时后释放资源。
- 延伸追问：令牌桶当前是否启用？

## 深入追问

- 主问题：为什么余票要按区间扣减？
- 第一层追问：A-D 的票会占用哪些区间？
- 第二层追问：如果只扣 A-D 会怎样？
- 回答思路：铁路座位是区间资源，A-D 会占用中间多个区间。项目通过 `listTakeoutTrainStationRoute` 找到需要扣减的区间。

## 设计思路

- 车票服务是项目核心，负责库存和座位这类强业务资源。
- 通过责任链隔离校验，通过策略模式隔离选座规则，通过 Redis 缓存提升查票性能。

## 未来可改进点

- 将查票默认入口切到 V2。
- 完整启用令牌桶，补齐扣减、回滚、校准闭环。
- 完善退票后座位释放和余票回滚。
- 补充热点线路缓存和压测数据。

## 面试表达建议

可以说：“车票服务是我最建议重点讲的模块。它不是简单查票，而是把查票性能、购票并发、座位分配、订单协作、库存回滚都串起来了。”

# order-service

## 模块职责

- 负责订单创建、订单查询、订单分页、本人订单查询。
- 负责订单关闭、取消、支付成功后的状态反转。
- 负责发送延迟关闭订单消息和消费支付/退款结果消息。

## 主要流程

- 创建订单：`createTicketOrder` 生成订单号，写订单主表、订单项、订单乘车人关系表。
- 延迟关闭：订单创建后发送 RocketMQ 延迟消息。
- 关闭订单：`closeTickOrder` 判断待支付状态后调用取消逻辑。
- 支付成功：`PayResultCallbackOrderConsumer` 消费支付消息，调用 `statusReversal` 和 `payCallbackOrder`。
- 本人订单：根据用户真实身份证号查询订单乘车人关系表。

## 涉及的关键类和方法

- `TicketOrderController`：订单接口。
- `OrderServiceImpl.createTicketOrder`：创建订单。
- `OrderServiceImpl.closeTickOrder/cancelTickOrder`：关闭和取消订单。
- `OrderServiceImpl.statusReversal/payCallbackOrder`：支付后状态更新。
- `OrderIdGeneratorManager.generateId`：订单号生成。
- `DelayCloseOrderSendProduce`：发送延迟关闭消息。
- `PayResultCallbackOrderConsumer`：消费支付结果。
- `shardingsphere-config.yaml`：订单分库分表和敏感字段加密配置。

## 面试常见问题

- 问题：订单创建时写了哪些表？
- 考察点：订单主表、订单项、乘客关系。
- 回答思路：写 `t_order`、`t_order_item`、`t_order_item_passenger`，分别表示订单、每张票和订单乘车人关系。
- 延伸追问：为什么要单独有乘车人关系表？

- 问题：未支付订单怎么关闭？
- 考察点：RocketMQ 延迟消息、订单状态判断。
- 回答思路：创建订单后发送延迟消息，到期后调用订单服务关闭；如果已支付则不释放座位。
- 延伸追问：延迟消息丢失怎么办？

## 深入追问

- 主问题：订单状态流转如何避免非法更新？
- 第一层追问：待支付、已支付、已关闭之间能不能随便跳？
- 第二层追问：支付成功和延迟关闭同时发生怎么办？
- 回答思路：当前通过状态判断限制关闭待支付订单；后续可抽象显式状态机，统一状态转移规则。

## 设计思路

- 订单服务只维护交易记录和订单状态，不直接操作车票库存。
- 用 MQ 把订单超时关闭和支付回调从同步流程中拆出来。

## 未来可改进点

- 引入订单状态机。
- 增加本地消息表或事务消息。
- 增加异常订单补偿任务。
- 完善退款后的订单项状态变更。

## 面试表达建议

可以说：“订单模块是交易状态中心。它不直接分配座位，但负责记录用户买了什么、订单处于什么状态，并通过消息推动超时关闭和支付后的状态变更。”

# pay-service

## 模块职责

- 负责支付单创建、支付查询、支付宝回调和退款。
- 通过策略模式支持不同支付渠道和交易类型。
- 支付成功后发送 MQ 通知订单和车票服务。

## 主要流程

- 创建支付：`PayController.pay` 转换支付命令，调用 `PayServiceImpl.commonPay`。
- 支付策略：通过 `AbstractStrategyChoose` 选择 `AliPayNativeHandler`。
- 回调处理：`PayCallbackController.callbackAlipay` 接收支付宝回调，选择 `AliPayCallbackHandler`。
- 更新支付单：`PayServiceImpl.callbackPay` 更新 `t_pay` 状态。
- 通知下游：支付成功后发送支付结果 MQ。
- 退款：`RefundController.commonRefund` 调用 `RefundServiceImpl.commonRefund`。

## 涉及的关键类和方法

- `PayController.pay`：创建支付。
- `PayCallbackController.callbackAlipay`：支付宝回调入口。
- `PayServiceImpl.commonPay/callbackPay`：支付单创建和回调更新。
- `RefundServiceImpl.commonRefund`：退款主逻辑。
- `AliPayNativeHandler`、`AliPayCallbackHandler`、`AliRefundNativeHandler`：支付和退款策略。
- `PayResultCallbackOrderSendProduce`：发送支付结果消息。
- `pay-service/shardingsphere-config.yaml`：支付表分片配置。

## 面试常见问题

- 问题：支付成功后怎么通知订单？
- 考察点：支付回调、MQ 解耦。
- 回答思路：支付服务更新支付单后发送支付结果 MQ，订单服务和车票服务分别消费。
- 延伸追问：回调重复通知怎么办？

- 问题：为什么用策略模式处理支付？
- 考察点：支付渠道扩展。
- 回答思路：不同支付渠道请求、回调、退款逻辑不同，用策略模式可以新增 handler，而不改主流程。
- 延伸追问：如果新增微信支付要改哪些类？

## 深入追问

- 主问题：支付回调如何保证安全？
- 第一层追问：如何确认回调来自支付宝？
- 第二层追问：金额、订单号、状态要不要校验？
- 回答思路：当前项目有回调 handler 和状态更新，生产化需要补签名校验、金额校验、状态幂等和重复回调处理。

## 设计思路

- 支付服务只负责支付域，不直接修改订单和座位。
- 支付结果通过消息通知业务服务，保持服务边界清晰。

## 未来可改进点

- 完善退款返回和订单状态闭环。
- 敏感密钥迁移到配置中心或密钥管理系统。
- 增加支付对账、退款对账。
- 增加回调验签和金额校验的面试表达准备。

## 面试表达建议

可以说：“支付模块的重点不是调支付宝接口本身，而是支付成功后如何可靠地驱动订单和座位状态变化。这里我会重点讲回调、MQ、幂等和最终一致性。”

# frameworks/base

## 模块职责

- 提供基础 Spring 上下文能力、应用初始化事件、全局常量和 Fastjson 安全模式。

## 主要流程

- 应用启动后，通过 `ApplicationContentPostProcessor` 发布初始化事件。
- `ApplicationContextHolder` 保存 Spring 容器，供策略、责任链等组件启动后取 Bean。

## 涉及的关键类和方法

- `ApplicationContextHolder.getBean/getBeansOfType`
- `ApplicationInitializingEvent`
- `ApplicationContentPostProcessor`
- `UserConstant`
- `FilterOrderConstant`

## 面试常见问题

- 问题：为什么需要 `ApplicationContextHolder`？
- 考察点：框架组件初始化和动态取 Bean。
- 回答思路：责任链、策略选择器在启动后需要扫描对应 Bean，使用上下文持有者统一获取。
- 延伸追问：过度使用会不会破坏依赖注入？

## 深入追问

- 主问题：为什么策略注册不用构造注入，而用启动事件扫描？
- 回答思路：因为策略数量不固定，启动后统一收集实现类，放入 Map，便于根据 mark 动态选择。

## 设计思路

- 把多个服务都会用到的基础能力沉淀成 starter。

## 未来可改进点

- 减少业务层直接调用 `ApplicationContextHolder`。
- 给初始化事件和 Bean 扫描增加异常提示。

## 面试表达建议

简单提即可，不建议作为主讲模块。

# frameworks/bizs/user

## 模块职责

- 提供用户上下文、用户信息传递过滤器和 JWT 工具。

## 主要流程

- 下游服务收到网关透传的请求头。
- `UserTransmitFilter` 读取用户信息，写入 `UserContext`。
- 请求结束后清理 ThreadLocal。

## 涉及的关键类和方法

- `UserContext`
- `UserTransmitFilter.doFilter`
- `JWTUtil.generateAccessToken/parseJwtToken`
- `UserAutoConfiguration`

## 面试常见问题

- 问题：业务层怎么获取当前用户？
- 考察点：ThreadLocal、请求上下文。
- 回答思路：网关写请求头，下游过滤器写 `UserContext`，业务层通过静态方法获取。
- 延伸追问：为什么用 `TransmittableThreadLocal`？

## 深入追问

- 主问题：ThreadLocal 不清理会怎样？
- 回答思路：线程池复用会导致用户信息串号或内存泄漏，所以 finally 中必须 remove。

## 设计思路

- 把用户上下文传递从业务服务中抽出来，多个服务复用。

## 未来可改进点

- 支持 traceId 与用户上下文一起透传。
- 增加下游服务来源校验，避免伪造请求头。

## 面试表达建议

可以和 gateway-service 一起讲，不要单独展开太久。

# frameworks/cache

## 模块职责

- 封装 Redis 缓存操作。
- 提供 `safeGet`、布隆过滤器、分布式锁保护等缓存防护能力。

## 主要流程

- 业务调用 `DistributedCache.safeGet`。
- 先查 Redis，未命中则获取 Redisson 分布式锁。
- 拿到锁后二次检查缓存。
- 仍未命中则调用 `CacheLoader` 加载数据库并写回缓存。

## 涉及的关键类和方法

- `DistributedCache`
- `StringRedisTemplateProxy.get/safeGet/put/delete`
- `CacheLoader`
- `BloomFilterPenetrateProperties`
- `CacheAutoConfiguration`

## 面试常见问题

- 问题：项目怎么防缓存击穿？
- 考察点：分布式锁、双重检查。
- 回答思路：`safeGet` 未命中时加锁，拿锁后二次查缓存，避免大量请求同时查库。
- 延伸追问：缓存穿透怎么处理？

## 深入追问

- 主问题：`safeGet` 如果数据库查询很慢怎么办？
- 回答思路：需要锁超时、降级、热点预热和监控，避免线程堆积。

## 设计思路

- 把缓存保护能力封装在公共模块，业务只关注如何加载数据。

## 未来可改进点

- 增加锁等待超时。
- 增加本地缓存组合。
- 增加缓存命中率监控。

## 面试表达建议

适合和查票性能一起讲：“查票使用 Redis，而公共 cache 模块提供了安全加载缓存的能力。”

# frameworks/designpattern

## 模块职责

- 提供责任链和策略模式基础能力。

## 主要流程

- 启动时扫描所有 `AbstractChainHandler`，按 mark 和 order 组织成责任链。
- 启动时扫描所有 `AbstractExecuteStrategy`，按 mark 注册到策略 Map。
- 业务根据 mark 执行对应链路或策略。

## 涉及的关键类和方法

- `AbstractChainContext.handler`
- `AbstractChainHandler`
- `AbstractStrategyChoose.chooseAndExecute/chooseAndExecuteResp`
- `AbstractExecuteStrategy`

## 面试常见问题

- 考察点：校验流程拆分。
- 回答思路：用户注册、查票、购票、退票校验都可以走责任链。
- 延伸追问：责任链顺序怎么保证？

## 深入追问

- 主问题：策略模式解决了什么问题？
- 回答思路：支付渠道和选座规则都有扩展需求，策略模式避免主流程大量 if-else。

## 设计思路

- 把变化点拆出去，主流程只负责调度。

## 未来可改进点

- 增加策略缺失时更明确的错误提示。

## 面试表达建议

# frameworks/idempotent

## 模块职责

- 提供接口和 MQ 消费幂等能力。
- 通过 `@Idempotent` 注解减少重复提交、重复消费风险。

## 主要流程

- AOP 拦截标注 `@Idempotent` 的方法。
- 根据场景 RESTAPI/MQ 和类型 SpEL/token/param 选择处理器。
- 执行业务前创建或检查幂等标识。
- 成功、失败、重复消费分别做后置处理。

## 涉及的关键类和方法

- `Idempotent`
- `IdempotentAspect.idempotentHandler`
- `IdempotentExecuteHandlerFactory`
- `IdempotentSpELByRestAPIExecuteHandler`
- `IdempotentSpELByMQExecuteHandler`
- `IdempotentTokenController`

## 面试常见问题

- 问题：有锁了为什么还要幂等？
- 考察点：锁和幂等职责区分。
- 回答思路：锁解决并发资源竞争，幂等解决重复请求或重复消息。
- 延伸追问：MQ 消费幂等 key 怎么设计？

## 深入追问

- 主问题：第一次执行失败后幂等 key 怎么处理？
- 回答思路：失败时要清理或标记可重试，项目切面里有异常处理入口，生产化要结合业务状态设计。

## 设计思路

- 幂等作为公共能力，避免每个接口重复写 Redis setIfAbsent。

## 未来可改进点

- 完善幂等状态机。
- 增加幂等 key 可观测性。
- 统一注解包名和场景封装。

## 面试表达建议

适合在支付回调、购票、MQ 重复消费场景中顺带讲。
