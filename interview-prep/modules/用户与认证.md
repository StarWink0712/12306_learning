# 面试准备：用户与认证模块

## 模块定位

用户与认证模块覆盖三块：

- 用户服务：注册、登录、注销、用户信息、乘车人管理。
- 网关鉴权：统一解析 JWT，透传用户信息。
- 用户上下文：下游服务通过 `UserContext` 获取当前登录用户。

这部分可以和购票主链路一起讲，因为购票需要当前用户和乘车人真实信息。

## 登录流程

核心方法是 `UserLoginServiceImpl.login`。

流程：

- 前端传入用户名、手机号或邮箱，以及密码。
- 如果包含 `@`，按邮箱查 `t_user_mail`。
- 否则先按手机号查 `t_user_phone`，查不到就把输入当用户名。
- 查询 `t_user`，校验用户名和密码。
- 构造 `UserInfoDTO`。
- 调用 `JWTUtil.generateAccessToken` 生成 JWT。
- 构造 `UserLoginRespDTO`。
- 把登录响应放入 Redis，过期时间 30 分钟。

注意：当前代码看起来是直接按密码字段查询，面试时要主动说生产环境应做 BCrypt/Argon2 等不可逆哈希存储，不能明文密码。

## 网关鉴权

核心类是 `TokenValidateGatewayFilterFactory`。

流程：

- Gateway 根据路径判断是否命中 `blackPathPre`。
- 命中后读取 `Authorization`。
- 用 `JWTUtil.parseJwtToken` 解析用户信息。
- 解析失败返回 401。
- 解析成功后，把 `userId`、`username`、`realName` 放到请求头。
- 如果是注销接口，还会把原 token 传给下游。

这个设计的好处是：登录态解析集中在网关，下游服务不用每个接口都解析 JWT。

## 下游用户上下文

核心类：

- `UserTransmitFilter`
- `UserContext`

流程：

- 下游服务收到网关透传的请求头。
- `UserTransmitFilter` 读取用户 ID、用户名、真实姓名、token。
- 写入 `UserContext`。
- `UserContext` 底层使用 `TransmittableThreadLocal`。
- 请求结束后在 finally 中 `removeUser`。

面试高频点：ThreadLocal 一定要清理，否则线程池复用可能导致用户信息串号或内存泄漏。

## 注册流程

核心方法是 `UserLoginServiceImpl.register`。

流程：

- 先走用户注册责任链 `USER_REGISTER_FILTER`。
- 按用户名获取 Redisson 分布式锁 `LOCK_USER_REGISTER + username`。
- 插入 `t_user`。
- 插入 `t_user_phone`。
- 如果有邮箱，插入 `t_user_mail`。
- 捕获唯一键冲突，返回用户名、手机号或邮箱已注册。
- 删除用户名复用记录。
- 从 Redis 用户名复用分片集合中移除。
- 加入注册布隆过滤器。

这里可以讲三层防重复：

- 责任链前置校验。
- Redisson 按用户名加锁。
- 数据库唯一约束兜底。

## 用户注销

核心方法是 `UserLoginServiceImpl.deletion`。

流程：

- 校验注销用户名和当前登录用户名一致。
- 按用户名加 Redisson 锁。
- 查询用户真实信息。
- 插入 `t_user_deletion`。
- 标记用户主表、手机号、邮箱删除时间。
- 删除 Redis 中当前 token。
- 插入 `t_user_reuse`。
- 把用户名加入 Redis 复用集合。

注销不是简单删除用户，而是要处理登录态、用户复用、历史订单展示等边界。

## 乘车人管理

乘车人相关类：

- `PassengerController`
- `PassengerServiceImpl`

乘车人列表会使用 `USER_PASSENGER_LIST` 缓存，新增、修改、删除后删除缓存，下一次查询重新加载。

新增、修改、删除接口上使用 `@Idempotent`，防止重复点击导致重复操作。

购票时，车票服务会通过 Feign 调用户服务，根据乘车人 ID 查询真实姓名、身份证、手机号等信息。

## 面试高频问题

- 问题：登录态怎么实现？
- 回答：登录成功后生成 JWT，同时把登录响应缓存到 Redis。网关解析 JWT 后把用户信息透传给下游，下游写入 `UserContext`。

- 问题：只解析 JWT 够不够？
- 回答：当前网关主要解析 JWT，生产化还应结合 Redis 登录态、token 黑名单、刷新 token 和踢下线能力。

- 问题：注册如何防止用户名重复？
- 回答：责任链先校验，按用户名加 Redisson 锁，数据库唯一索引兜底，同时维护布隆过滤器和用户名复用集合。

- 问题：业务层怎么拿当前用户？
- 回答：网关透传请求头，下游 `UserTransmitFilter` 写入 `UserContext`，业务代码通过静态方法获取，finally 清理上下文。

## 需要谨慎表达

- 当前密码处理不适合作为生产方案，要主动说明应使用不可逆哈希和盐。
- 网关解析 JWT 后没有明显每次查 Redis 登录态，注销后 JWT 未过期的问题需要 token 黑名单或 Redis 状态校验补强。
- 下游信任请求头有伪造风险，生产上应限制下游服务入口或做服务间鉴权。
- `TransmittableThreadLocal` 能传递上下文，但也更要重视清理。

## 一句话总结

用户认证模块可以概括为：用户服务负责账号和乘车人，网关统一解析 JWT，下游通过用户上下文获取身份，生产化还需要补强密码安全和 token 生命周期。
