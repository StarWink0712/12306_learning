# 面试准备：并发控制模块

## 模块定位

并发控制主要服务于购票、订单取消、注册、缓存加载和 MQ 消费这些“同一资源可能被重复操作”的场景。

这个项目里最值得讲的是购票并发：同一车次、同一席别会在短时间内被大量用户争抢，系统既要避免超卖，也要避免重复下单、重复扣减、重复释放。

## 购票并发链路

购票入口在 `TicketServiceImpl.purchaseTicketsV1/purchaseTicketsV2`。

V1 的思路比较保守：

- 先走购票责任链，校验参数、车次、乘车人、余票和重复购买。
- 按 `trainId` 构造 Redisson 分布式锁。
- 锁内执行 `executePurchaseTickets`，完成选座、锁座、保存车票、远程创建订单。
- 好处是简单，风险是锁粒度粗，同一车次不同席别也会互相阻塞。

V2 的思路更贴近业务资源：

- 按乘车人的 `seatType` 分组。
- 锁 key 从“车次”细化成“车次 + 席别”，对应 `LOCK_PURCHASE_TICKETS_V2`。
- 同一 JVM 内用 Caffeine 缓存 `ReentrantLock`，减少本机线程竞争。
- 多实例之间用 Redisson 公平锁，保证跨节点互斥。
- 拿到锁后再调用 `executePurchaseTickets`。

面试里可以这样说：V2 的核心不是“多加了一把锁”，而是把锁粒度从整车次降到车次加席别，让锁和真实竞争资源对齐。

## 幂等和锁的分工

锁解决的是并发资源竞争，幂等解决的是同一业务动作重复执行。

项目中两类机制同时存在：

- `purchaseTicketsV1/V2` 上有 `@Idempotent`，防止用户重复点击购票。
- 购票锁保护座位分配和库存扣减，防止并发超卖。
- 支付创建、乘车人增删改、MQ consumer 也使用 `@Idempotent`。
- MQ 场景下，`IdempotentSpELByMQExecuteHandler` 用 Redis + Lua 记录消费中和已消费状态。

回答“有锁了为什么还要幂等”时，可以直接说：锁挡的是多个请求同时改同一资源，幂等挡的是同一个请求被重复执行，两者不是替代关系。

## 防超卖思路

项目防超卖不是只靠一个库存字段。

主要有四层：

- 入口校验：`TrainPurchaseTicketParamStockChainHandler` 先查 `TRAIN_STATION_REMAINING_TICKET` 余票缓存。
- 互斥控制：购票 V2 按车次和席别加本地锁、分布式锁。
- 座位状态：`SeatServiceImpl.lockSeat` 把占用区间的座位改为 `LOCKED`。
- 缓存扣减：`AbstractTrainPurchaseTicketTemplate.executeResp` 按经过区间扣减 Redis 余票。

支付成功后，`PayResultCallbackTicketConsumer` 把座位改为 `SOLD`。订单超时关闭或主动取消时，`DelayCloseOrderConsumer`、`cancelTicketOrder` 会释放座位并回滚余票缓存。

## 令牌桶方案

项目里保留了 `TicketAvailabilityTokenBucket` 和 Lua 脚本方案：

- `ticket_availability_token_bucket.lua` 用于原子扣令牌。
- `ticket_availability_rollback_token_bucket.lua` 用于取消或超时关闭后回滚令牌。
- token bucket key 是 `TICKET_AVAILABILITY_TOKEN_BUCKET + trainId`。

但要注意：`purchaseTicketsV2` 里取令牌的代码当前被注释了。所以面试时不要说“当前主链路完全依赖令牌桶防超卖”，更稳妥的说法是：项目保留了令牌桶前置限流方案，当前主链路更明确的是锁、选座、座位状态和 Redis 余票扣减。

## 订单并发

订单取消和状态反转也有并发保护：

- `OrderServiceImpl.cancelTickOrder` 按 `orderSn` 加 Redisson 锁，防止同一订单被重复取消。
- `closeTickOrder` 先检查订单是否仍是 `PENDING_PAYMENT`，已支付就不关闭。
- `statusReversal` 支付成功时也按订单号加锁，防止重复状态修改。

可以把它讲成：订单状态更新不只依赖锁，还要先看当前状态，只有合法状态才能进入下一步。

## 缓存并发

公共缓存模块 `StringRedisTemplateProxy.safeGet` 用分布式锁防缓存击穿：

- 先查 Redis。
- 未命中后获取 `safe_get_distributed_lock_get:` 前缀的 Redisson 锁。
- 拿到锁后二次检查缓存。
- 仍未命中再执行 `CacheLoader` 查库并写缓存。

这适合回答“热点缓存失效后大量请求打数据库怎么办”。

## 面试高频问题

- 问题：项目如何防止超卖？
- 回答：责任链先校验余票，购票 V2 按车次和席别加锁，锁内选座并锁定区间座位，同时扣减经过区间的 Redis 余票；支付成功改已售，取消或超时关闭会回滚。

- 问题：V1 和 V2 的锁有什么区别？
- 回答：V1 按车次加锁，简单但粒度粗；V2 按车次加席别加锁，并结合本地锁和 Redisson 公平锁，减少不同席别之间无意义的等待。

- 问题：本地锁和分布式锁都用是不是重复？
- 回答：不重复。本地锁降低单实例内线程竞争，分布式锁保证多实例互斥。它们保护的范围不同。

- 问题：锁粒度越细越好吗？
- 回答：不是。锁越细并发度越高，但多锁顺序、死锁、回滚复杂度也会上升。项目按席别细化，是因为席别是比较自然的库存竞争粒度。

## 需要谨慎表达

- 当前 `lockSeat` 更新座位时没有明显使用 `seat_status = AVAILABLE` 作为乐观条件并检查影响行数，面试时可以说生产化应补充状态条件和失败回滚。
- 令牌桶实现存在，但购票 V2 取令牌逻辑被注释，不能夸成主链路已完整启用。
- 多把锁最好固定排序并设置超时获取，当前代码是按分组遍历加锁，生产化还可以更严谨。

## 一句话总结

并发控制这块可以概括为：购票用“责任链校验 + 细粒度锁 + 座位状态 + 区间余票扣减 + 幂等 + 关闭回滚”共同防止超卖和重复执行。
