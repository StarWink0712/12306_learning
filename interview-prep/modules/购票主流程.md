# 面试准备：购票主流程模块

## 模块定位

购票主流程是这个项目最适合重点讲的部分，因为它把用户、车票、订单、支付、缓存、锁、消息队列都串起来了。

面试时不要只说“用户下单买票”，要按“查票、校验、加锁、选座、锁座、建单、支付、关闭回滚”这条链路讲。

## 完整主链路

### 1. 登录和用户上下文

用户先调用用户服务登录。

- `UserLoginServiceImpl.login` 支持用户名、手机号、邮箱登录。
- 登录成功后用 `JWTUtil.generateAccessToken` 生成 JWT。
- 登录响应写入 Redis，默认 30 分钟。
- 网关 `TokenValidateGatewayFilterFactory` 解析 `Authorization`，把用户信息写入请求头。
- 下游 `UserTransmitFilter` 写入 `UserContext`，业务代码直接通过 `UserContext.getUsername/getUserId` 获取当前用户。

### 2. 查询车票

查票入口是 `TicketController.pageListTicketQuery`，当前默认调用 `pageListTicketQueryV1`。

- 先走查票责任链，校验城市、站点、日期等参数。
- 查询站点映射、地区车次映射。
- 查询车次信息、价格、余票。
- 返回车次列表、出发站列表、到达站列表、列车品牌、席别等。

V2 查询 `pageListTicketQueryV2` 使用 Redis pipeline 批量取价格和余票，优化点是减少网络往返。

### 3. 提交购票

购票入口是 `TicketController.purchaseTickets/purchaseTicketsV2`。

`purchaseTicketsV2` 的核心流程：

- 走购票责任链：参数非空、业务合法性、余票、重复购买等。
- 按乘客选择的 `seatType` 分组。
- 为每个席别构造“车次 + 席别”的锁 key。
- 本机用 `ReentrantLock`，多实例用 Redisson 公平锁。
- 锁内调用 `executePurchaseTickets`。

### 4. 选座

`executePurchaseTickets` 会先从缓存读取车次信息：

- key 是 `TRAIN_INFO + trainId`。
- 通过 `distributedCache.safeGet` 加载，缓存过期按提前售票天数设置。

然后进入选座：

- `TrainSeatTypeSelector.select` 按座位类型分组。
- 如果有多种席别，可以使用线程池并行处理。
- 根据“列车类型 + 座位类型”选择具体 handler。
- 具体 handler 负责选座、查询乘车人真实信息、计算票价、锁座。

### 5. 锁座和扣减余票

选座完成后，`SeatServiceImpl.lockSeat` 把覆盖区间的座位状态更新为 `LOCKED`。

`AbstractTrainPurchaseTicketTemplate.executeResp` 会根据 `trainStationService.listTakeoutTrainStationRoute` 计算经过区间，并扣减 Redis 里的 `TRAIN_STATION_REMAINING_TICKET`。

这里的重点是：一张票会占用多个区间，不是简单扣一个库存字段。

### 6. 保存车票并创建订单

`executePurchaseTickets` 会保存 `TicketDO`：

- 车票状态是 `TicketStatusEnum.UNPAID`。
- 保存的是用户、车次、车厢、座位、乘车人等信息。

然后组装 `TicketOrderCreateRemoteReqDTO`，通过 Feign 调用订单服务：

- 订单服务 `OrderServiceImpl.createTicketOrder` 生成订单号。
- 写入 `t_order`、`t_order_item`、`t_order_item_passenger`。
- 订单初始状态是 `PENDING_PAYMENT`。
- 发送 RocketMQ 延迟关闭订单消息。

### 7. 支付和回调

支付服务负责创建支付单和处理支付宝回调。

- `PayServiceImpl.commonPay` 创建支付记录。
- `PayCallbackController.callbackAlipay` 接收支付宝回调。
- `PayServiceImpl.callbackPay` 更新支付单状态。
- 支付成功后发送 MQ。

订单服务消费支付结果后更新订单状态；车票服务消费支付结果后把座位状态改为 `SOLD`。

### 8. 超时关闭

订单创建后如果用户没有支付：

- RocketMQ 延迟消息到期。
- `DelayCloseOrderConsumer` 调用订单服务 `closeTickOrder`。
- 如果订单仍是待支付，关闭订单。
- 释放数据库座位。
- 回滚 Redis 余票。
- 回滚令牌桶。

## 关键类

- `TicketController`：查票、购票、取消、支付查询、退票入口。
- `TicketServiceImpl.pageListTicketQueryV1/V2`：查票。
- `TicketServiceImpl.purchaseTicketsV1/V2`：购票入口和锁。
- `TicketServiceImpl.executePurchaseTickets`：购票主执行链路。
- `TrainSeatTypeSelector`：选座策略入口。
- `AbstractTrainPurchaseTicketTemplate`：选座后扣减区间余票。
- `SeatServiceImpl`：锁座和解锁。
- `TicketOrderRemoteService`：车票服务远程调用订单服务。
- `OrderServiceImpl.createTicketOrder`：订单创建。
- `DelayCloseOrderConsumer`：超时关闭释放资源。
- `PayResultCallbackTicketConsumer`：支付成功后更新座位。

## 面试高频问题

- 问题：用户点击购票后后端发生了什么？
- 回答：先责任链校验，再按车次和席别加锁，锁内选座和锁座，保存车票记录，远程调用订单服务创建待支付订单，订单创建后投递延迟关闭消息，支付成功后再通过 MQ 更新订单和座位状态。

- 问题：为什么先锁座再创建订单？
- 回答：订单里需要明确的车厢座位信息，所以先选座、锁座，再创建待支付订单。风险是跨服务一致性，需要用异常回滚、延迟关闭和补偿兜底。

- 问题：如果订单服务创建失败怎么办？
- 回答：当前代码会抛异常触发车票服务本地事务回滚，生产化还需要补偿任务确保已锁座位和缓存余票能被释放。

- 问题：为什么支付成功后用 MQ，而不是支付服务直接改订单和座位？
- 回答：订单和座位分别属于订单服务和车票服务，支付服务只负责支付域。MQ 让状态流转异步解耦，每个服务维护自己的数据边界。

## 可改进点

- 查票 Controller 默认仍调用 V1，可切到 V2 后压测验证。
- 购票远程创建订单属于跨服务操作，可引入本地消息表、事务消息或 Saga 补强可靠性。
- 令牌桶方案可以补完整闭环，作为锁前的前置限流。
- 超时关闭不能只依赖延迟消息，生产上应加定时补偿任务扫描长时间锁定座位。

## 一句话总结

购票主流程可以这样讲：车票服务负责高并发查票和选座锁座，订单服务负责待支付订单和状态，支付服务通过 MQ 驱动订单和座位最终确认。
