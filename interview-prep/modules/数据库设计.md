# 面试准备：数据库设计模块

## 模块定位

数据库设计要围绕业务边界讲，不要只背表名。

这个项目的数据大致分成四类：

- 用户域：用户、手机号、邮箱、乘车人、注销和用户名复用。
- 车票域：车站、车次、车厢、座位、价格、车票记录。
- 订单域：订单主表、订单项、订单乘车人关系。
- 支付域：支付单、退款单。

## 用户服务表

用户服务核心实体：

- `UserDO -> t_user`：用户主表。
- `UserPhoneDO -> t_user_phone`：手机号和用户名关系。
- `UserMailDO -> t_user_mail`：邮箱和用户名关系。
- `PassengerDO`：乘车人信息。
- `UserDeletionDO -> t_user_deletion`：注销记录。
- `UserReuseDO -> t_user_reuse`：用户名复用记录。

注册时会写用户主表、手机号表、邮箱表。注销时会写注销记录、软删除用户相关记录、把用户名加入复用集合。

面试可以说：手机号、邮箱拆表是为了支持多登录方式和唯一性校验，同时避免用户主表过度承载所有查询。

## 车票服务表

车票服务核心实体：

- `TrainDO`：车次基础信息。
- `StationDO`：车站。
- `TrainStationDO`：车次经过站点。
- `TrainStationRelationDO`：站点区间关系。
- `TrainStationPriceDO`：区间席别价格。
- `CarriageDO`：车厢。
- `SeatDO -> t_seat`：座位和区间状态。
- `TicketDO -> t_ticket`：用户购票后的车票记录。

最重要的是 `t_seat`。它不是只存一个物理座位，而是和起终站区间有关，座位状态有 `AVAILABLE`、`LOCKED`、`SOLD`。

购票时：

- 根据 `TrainStationRelationDO` 找到用户购买覆盖的区间。
- 更新这些区间上的座位状态。
- 保存 `TicketDO`，初始是未支付。

## 订单服务表

订单服务核心表：

- `t_order`：订单主表，记录订单号、用户、车次、出发到达、时间、支付状态等。
- `t_order_item`：订单项，每张票一条，记录乘客、席别、座位、金额、订单项状态。
- `t_order_item_passenger`：订单和乘车人证件关系，用于本人订单查询。

为什么要有订单项：

- 一个订单可以有多个乘车人。
- 后续部分退款、单人退票、改签都需要按单张票维护状态。

为什么要有乘车人关系表：

- 用户 A 可以帮用户 B 买票。
- B 查询“本人订单”时，不应该只查自己下的订单，而要查身份证作为乘车人的订单。

## 支付服务表

支付服务核心表：

- `t_pay`：支付单，记录订单号、支付流水号、支付渠道、金额、支付状态、支付时间等。
- `t_refund`：退款单，记录退款流水、订单号、退款类型、退款金额和状态。

支付服务只维护支付域数据。支付成功后通过 MQ 通知订单和车票服务，不直接跨库修改它们的数据。

## 分库分表

订单服务 ShardingSphere 配置：

- 数据源：`ds_0`、`ds_1`。
- `t_order` 实际节点：`ds_${0..1}.t_order_${0..31}`。
- `t_order_item` 实际节点：`ds_${0..1}.t_order_item_${0..31}`。
- `t_order_item_passenger` 实际节点：`ds_${0..1}.t_order_item_passenger_${0..31}`。
- `t_order`、`t_order_item` 分片列：`user_id, order_sn`。
- `t_order_item_passenger` 分片列：`id_card`。

支付服务 ShardingSphere 配置：

- `t_pay` 实际节点：`ds_${0..1}.t_pay_${0..31}`。
- 分片列：`order_sn, pay_sn`。

面试表达重点：分片键要服务查询路径。订单有用户订单列表和订单详情查询，所以使用用户 ID 和订单号；本人订单按身份证查，所以乘车人关系表按身份证分片。

## 敏感数据

订单服务配置了 ShardingSphere 加密：

- `t_order_item.id_card` 使用 AES。
- `t_order_item.phone` 使用 AES。
- `queryWithCipherColumn: true`。

项目里还有手机号、身份证脱敏序列化类。

可以这样讲：加密解决落盘安全，脱敏解决接口展示和日志展示安全，它们不是同一层问题。

## 事务边界

本地事务：

- `OrderServiceImpl.createTicketOrder`：订单主表、订单项、乘客关系。
- `OrderServiceImpl.cancelTickOrder`：订单和订单项状态。
- `TicketServiceImpl.executePurchaseTickets`：车票服务本地保存车票记录。
- `PayServiceImpl.commonPay/callbackPay`：支付单创建和回调状态。

跨服务风险：

- 车票服务锁座后调用订单服务，Feign 调用不在同一个本地事务。
- 支付服务更新支付单后发送 MQ，也涉及本地状态和消息投递一致性。

生产化回答：可以用本地消息表、事务消息或 Saga 补偿来增强跨服务一致性。

## 面试高频问题

- 问题：订单为什么拆主表和订单项？
- 回答：一个订单可能包含多张票，订单主表表达整单，订单项表达单张票，方便部分退款、单人退票和订单详情展示。

- 问题：为什么本人订单要通过身份证关系表查？
- 回答：买票人和乘车人不一定是同一个人。本人订单应该按当前用户真实证件号查询乘车人关系。

- 问题：分片键为什么这样选？
- 回答：订单常见查询是用户维度和订单号维度，支付常见查询是订单号和支付流水号，分片键要贴近这些查询路径。

- 问题：加密和脱敏有什么区别？
- 回答：加密保护数据库落盘数据，脱敏保护接口返回和日志展示，二者解决的问题不同。

## 可改进点

- 补充关键表的唯一索引和普通索引说明，比如订单号、用户 ID、证件号、车次区间。
- 对 `t_seat` 锁座更新增加状态条件和影响行数校验。
- 对跨服务事务链路增加可靠消息或补偿表。
- 密钥、数据库密码不应硬编码在配置里，生产要接配置中心或密钥管理。

## 一句话总结

数据库设计可以概括为：用户、车票、订单、支付按业务域拆表，订单和支付做分片扩展，敏感字段加密，跨服务一致性靠消息和补偿而不是一个大事务。
