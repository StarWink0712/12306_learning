# 一、功能层面的可改进点

## 1. 进一步完善退票和退款闭环

- 当前现状：项目已经有退票入口 `TicketController.commonTicketRefund`，车票服务会查询订单详情并调用支付服务退款；支付服务里也有 `RefundServiceImpl.commonRefund` 创建退款记录、调用退款策略、发送退款结果消息。但部分返回值仍是 `null` 或 TODO，例如 `RefundServiceImpl` 和 `PayServiceImpl.commonRefund` 里有“后续完善返回逻辑”的痕迹。
- 为什么值得改：购票系统里“买票”只是前半段，退票退款同样是用户高频操作。如果退款结果、订单状态、座位释放没有完整闭环，面试时容易被追问一致性和业务完整度。
- 可以怎么改：补齐退款响应 DTO，明确全额退款、部分退款的状态流转；订单服务消费退款结果后更新订单和订单项状态；车票服务根据退款明细释放对应座位和区间余票；增加退款失败、重复退款、部分退款边界校验。
- 改完能带来什么收益：整个交易链路从“购票支付”扩展到“购票、支付、退票、退款”，业务闭环更完整，也更接近真实票务系统。
- 面试里可以怎么表达：目前项目主链路更完整的是查票、购票、支付和超时关闭；如果继续迭代，我会优先把退票退款做成和支付一样可靠的事件驱动闭环，包括状态机、退款明细、消息幂等和失败补偿。

## 2. 补充更完整的订单状态机

- 当前现状：订单服务里 `OrderStatusEnum` 定义了待支付、已支付、部分退款、全部退款、已完成、已关闭等状态，`OrderServiceImpl` 里也有关闭订单、支付成功状态反转等逻辑。
- 为什么值得改：现在状态更新主要散落在不同方法中，依赖代码里的条件判断。随着退票、改签、候补、支付超时等场景增加，状态流转会越来越复杂。
- 可以怎么改：抽象订单状态机，明确“当前状态、事件、目标状态、允许动作”，比如待支付只能支付成功或关闭，已支付才能退票，已关闭不能再支付成功。可以把状态校验从业务方法中收敛到统一组件。
- 改完能带来什么收益：减少非法状态跳转，降低后续扩展复杂度，也方便面试时讲清楚订单生命周期。
- 面试里可以怎么表达：现在项目已经有订单状态枚举和基础状态流转，后续我会把它演进成显式状态机，核心目标是让每一次订单状态变化都有明确入口和校验规则。

## 3. 完善乘车人和购票风控校验

- 当前现状：乘车人新增、修改、删除已经有参数校验和幂等控制；购票责任链里也有参数校验、库存校验、重复购买校验入口，但 `TrainPurchaseTicketRepeatChainHandler` 中重复购买验证还有 TODO，购票参数校验处也有风控相关 TODO。
- 为什么值得改：真实购票系统需要防止同一乘车人重复购买同一车次、异常频繁请求、恶意刷票等行为。
- 可以怎么改：补齐同一乘车人同一车次同一日期的重复购买检查；增加用户维度、IP 维度、车次维度的频率限制；异常请求记录到风控表或日志；对高风险用户做验证码、限流或临时拦截。
- 改完能带来什么收益：能减少重复占座和恶意请求，提升购票公平性和系统稳定性。
- 面试里可以怎么表达：我不会把购票只理解成库存扣减，真实场景还要考虑用户行为校验和风控。这个项目后续可以把责任链继续扩展，把重复购买和异常请求识别做得更完整。

## 4. 增加改签、候补等票务扩展能力

- 当前现状：当前项目覆盖了用户、查票、购票、订单、支付、取消、退款的主要链路，但还没有改签、候补、排队等更复杂的票务能力。
- 为什么值得改：12306 场景里，改签和候补能更好体现票务系统的业务深度，也能自然引出订单状态、库存释放、消息补偿等复杂设计。
- 可以怎么改：改签可以设计为“原票释放 + 新票锁定 + 差价支付/退款”的复合事务；候补可以用队列保存用户需求，当余票释放时异步匹配候补订单。
- 改完能带来什么收益：项目从基础购票系统升级为更完整的票务交易系统，业务复杂度和面试可讲内容都会更丰富。
- 面试里可以怎么表达：当前项目先保证核心购票链路可讲清楚，后续如果继续做深，我会优先围绕改签和候补扩展，因为这两个功能最能体现票务系统和普通电商系统的差异。

# 二、架构层面的可改进点

## 5. 引入聚合服务或 BFF 层

- 当前现状：网关里有 `application-aggregation.yaml`，路由指向 aggregation 服务，但 `services/pom.xml` 中 `aggregation-service` 被注释掉了，当前实际主线是网关直接路由到用户、车票、订单、支付服务。
- 为什么值得改：前端页面往往需要组合多个服务的数据，比如订单详情页可能同时要订单、乘客、支付单、车票信息。如果都由前端分别调多个服务，接口编排会分散。
- 可以怎么改：增加 aggregation-service 或 BFF 层，专门做面向页面的数据编排，例如订单详情聚合、购票确认页聚合。它只做查询聚合和流程编排，不直接承载核心库存和订单状态变更。
- 改完能带来什么收益：前端调用更简单，服务间编排更集中，也能减少前端感知后端服务拆分细节。
- 面试里可以怎么表达：当前项目已经有聚合服务的配置痕迹，但主链路还没有启用。我后续会把它定位为 BFF，只负责页面级聚合，不把核心业务规则写进去，避免网关或前端承担过多编排逻辑。

## 6. 优化跨服务调用的容错设计

- 当前现状：车票服务通过 Feign 调用订单、用户、支付服务；支付服务也会调用订单服务。当前代码对远程调用失败主要是记录日志、抛异常，依赖上层事务或补偿逻辑兜底。
- 为什么值得改：购票链路里远程调用失败会带来座位锁定、订单创建、支付状态不一致等问题。只抛异常对用户和系统都不够友好。
- 可以怎么改：为关键 Feign 调用增加超时、熔断和降级策略；远程创建订单使用业务幂等号；失败时记录补偿任务；对用户返回“处理中”或可查询的订单状态，而不是简单失败。
- 改完能带来什么收益：服务间依赖更稳，局部服务故障不会无限放大，用户也能通过查询最终状态获得确定结果。
- 面试里可以怎么表达：现在项目已经完成服务拆分和 Feign 调用，后续我会把重点放在远程调用失败后的业务兜底，比如幂等业务号、补偿记录和降级返回。

## 7. 收敛包名、模块依赖和历史遗留配置

- 当前现状：源码中存在 `com.guoxu`、`org.opengoofy.index12306` 等包名和依赖命名混用；部分模块或配置有历史遗留，例如 aggregation 服务配置存在但模块被注释。
- 为什么值得改：这些问题不一定影响核心业务理解，但会影响工程可维护性，也容易让新人阅读代码时困惑。
- 可以怎么改：统一包名前缀和 artifactId 命名；清理未启用模块配置；删除或迁移 Deprecated 的临时接口；把学习注释和生产注释区分开。
- 改完能带来什么收益：项目结构更清晰，依赖关系更干净，后续扩展和排查问题更方便。
- 面试里可以怎么表达：这个项目有学习和二次整理痕迹，后续如果要走向更正式的工程，我会先做模块和命名治理，让业务边界和依赖关系更清楚。

# 三、并发与性能层面的可改进点

## 8. 将查票接口默认切换到 V2 或继续演进 V3

- 当前现状：`TicketServiceImpl` 里有 `pageListTicketQueryV1` 和 `pageListTicketQueryV2`，V2 使用 Redis pipeline 批量获取价格和余票，明显是针对 V1 循环访问 Redis 的优化。但 `TicketController.pageListTicketQuery` 当前默认调用的是 V1。
- 为什么值得改：查票是典型高频读接口，Redis 网络往返次数会直接影响接口耗时和吞吐。
- 可以怎么改：把默认查询切换到 V2；对 V2 做压测对比；继续减少 JSON 反序列化和 Java 侧组装成本；对热门线路做本地缓存或预聚合缓存。
- 改完能带来什么收益：降低查票接口延迟，提高高峰期吞吐，也能形成清晰的性能优化案例。
- 面试里可以怎么表达：我会把 V1 作为易理解版本，把 V2 作为优化版本。后续真正上线会默认走 V2，并通过压测数据说明 pipeline 对 Redis 往返次数的优化效果。

## 9. 完整启用和校准余票令牌桶方案

- 当前现状：项目里有 `TicketAvailabilityTokenBucket` 和 Lua 脚本，支持令牌初始化、扣减和回滚；但 `purchaseTicketsV2` 中获取令牌的逻辑目前被注释，当前主链路主要靠锁、选座、座位状态和余票缓存。
- 为什么值得改：在热门车次高并发抢票场景下，如果大量无票请求都进入锁和选座流程，会增加服务压力。令牌桶可以在更前面挡掉明显无票请求。
- 可以怎么改：重新启用令牌桶扣减；确保购票失败、订单取消、超时关闭、退款等场景都能回滚令牌；增加令牌和真实座位库存的定时校准；Lua 脚本保持多区间多席别原子扣减。
- 改完能带来什么收益：减少无效请求进入核心购票逻辑，降低锁竞争和数据库压力，提高热门车次抗压能力。
- 面试里可以怎么表达：项目里已经有令牌桶雏形，但我不会简单说“用了令牌桶”。更准确的表达是：当前主链路靠锁和座位状态，后续可以把令牌桶补成完整前置限流和库存预扣减方案。

## 10. 进一步优化购票锁粒度和锁获取方式

- 当前现状：购票 V2 已经从 V1 的整车次锁优化为“车次 + 座位类型”锁，并组合 Caffeine 本地锁和 Redisson 公平锁。
- 为什么值得改：锁粒度细化提高了并发度，但多把锁、锁等待、锁释放异常等问题也会带来复杂度。
- 可以怎么改：为锁获取增加超时时间和失败降级；多席别购票时固定锁排序，降低死锁风险；监控锁等待时间；根据压测结果决定是否保留公平锁或改为普通锁提升吞吐。
- 改完能带来什么收益：在保证不超卖的前提下减少无效等待，提高购票接口稳定性和吞吐。
- 面试里可以怎么表达：我理解锁不是越多越好，后续优化会围绕“锁粒度、锁等待、锁超时、锁监控”来做，用业务资源粒度控制并发，而不是简单全局加锁。

## 11. 增加热点数据本地缓存和请求合并

- 当前现状：项目已经使用 Redis 缓存车次、站点、价格、余票，也使用 Caffeine 缓存本地锁对象，但车票查询结果和热门静态数据还可以进一步优化。
- 为什么值得改：春运类场景下，热门线路查询会高度集中，单纯依赖 Redis 仍可能出现热点 key 压力。
- 可以怎么改：对车次基础信息、站点映射、价格等低频变更数据增加 Caffeine 本地缓存；对同一时间窗口内相同查票请求做请求合并；热点 key 做分片或读副本；配置缓存更新通知。
- 改完能带来什么收益：降低 Redis 热点压力，减少重复计算和重复网络访问。
- 面试里可以怎么表达：Redis 解决了数据库压力，但热门线路下 Redis 自身也可能变成瓶颈。后续我会把静态数据再加一层本地缓存，余票这种强变化数据仍以 Redis 为主。

# 四、数据一致性与稳定性层面的可改进点

## 12. 引入本地消息表或事务消息

- 当前现状：订单创建时会在 `OrderServiceImpl.createTicketOrder` 中写订单并发送 RocketMQ 延迟关闭消息；支付回调后 `PayServiceImpl.callbackPay` 更新支付单并发送支付结果消息。当前逻辑主要依赖方法异常来回滚。
- 为什么值得改：本地数据库事务和 MQ 发送不是天然原子操作，极端情况下可能出现数据库提交成功但消息没有可靠投递的问题。
- 可以怎么改：引入本地消息表，在本地事务里同时写业务数据和待发送消息，再由后台任务可靠投递；或者使用 RocketMQ 事务消息。消费者继续保持幂等处理。
- 改完能带来什么收益：订单超时关闭、支付结果通知、退款结果通知这些关键事件更可靠，减少跨服务状态不一致。
- 面试里可以怎么表达：项目当前已经用 MQ 做异步解耦，后续我会补可靠消息机制，让“业务数据变更”和“消息一定被投递”形成更强的最终一致保障。

## 13. 增加异常状态补偿任务

- 当前现状：项目通过延迟消息关闭未支付订单，通过 MQ 消费更新支付后的订单和座位状态；但如果消息丢失、消费失败超过重试、服务宕机，仍需要兜底机制。
- 为什么值得改：票务系统对状态一致性要求高，不能只依赖单次消息链路。
- 可以怎么改：增加补偿任务扫描异常状态，例如待支付超时未关闭、订单已支付但座位仍锁定、支付单成功但订单未支付、退款成功但订单未更新。补偿任务需要幂等，按业务单号处理。
- 改完能带来什么收益：系统从“流程正常时可用”提升为“异常情况下可自愈”，稳定性更强。
- 面试里可以怎么表达：真实系统里我不会只依赖 MQ 一条链路，关键状态都会设计补偿扫描和对账任务，保证最终状态能被修正。

## 14. 完善缓存一致性校准机制

- 当前现状：项目支持两类余票更新思路：业务流程中直接扣减/回滚 Redis 余票；以及通过 Canal binlog 消费 `t_seat` 变化更新缓存。代码中通过 `ticket.availability.cache-update.type` 判断是否走 binlog 模式。
- 为什么值得改：余票缓存是用户感知最强的数据，如果缓存与数据库座位状态长期不一致，会造成有票买不了或无票还能下单。
- 可以怎么改：明确一种主策略，例如业务扣减为主、Canal 校准为辅；增加定时对账任务，按车次和区间重新计算座位状态并修正 Redis；给余票缓存增加版本号或更新时间监控。
- 改完能带来什么收益：余票展示和真实座位状态更一致，异常恢复能力更好。
- 面试里可以怎么表达：当前项目已经有业务扣减和 binlog 同步两种方向，后续我会把它设计成“实时扣减 + 异步校准 + 定时对账”的组合，而不是只靠某一个环节。

## 15. 强化配置和密钥安全

- 当前现状：`pay-service/application.yaml` 中包含支付宝沙箱配置，数据库、Redis 等连接信息也写在本地配置里。
- 为什么值得改：这些信息在学习环境可以方便运行，但生产环境不能把密钥、密码直接放在代码仓库。
- 可以怎么改：接入 Nacos 配置中心或环境变量管理敏感配置；密钥使用专门的密钥管理系统；不同环境使用不同配置；敏感日志脱敏。
- 改完能带来什么收益：降低密钥泄露风险，提高多环境部署的安全性和规范性。
- 面试里可以怎么表达：这个项目目前更偏学习环境配置，后续生产化我会把数据库密码、Redis 密码、支付宝密钥等全部迁到配置中心或密钥系统，并做好权限控制。

# 五、工程化层面的可改进点

## 16. 补充核心链路测试和压测

- 当前现状：项目有测试目录和测试类，但核心链路的单元测试、集成测试、并发压测还不充分。查票 V1/V2、购票 V1/V2 也缺少可复现的压测报告。
- 为什么值得改：面试时如果能讲出“我怎么验证优化有效”，会比只讲设计更有说服力。
- 可以怎么改：为责任链、幂等、订单状态流转、退款、分片算法写单元测试；用 Testcontainers 或本地 Docker 编排 Redis、MySQL、RocketMQ 做集成测试；用 JMeter/Gatling 压测查票和购票接口。
- 改完能带来什么收益：能更早发现回归问题，也能用数据证明性能优化效果。
- 面试里可以怎么表达：后续我会补两类验证：一类是业务正确性的自动化测试，一类是查票和购票的压测。这样项目不是只停留在“我认为能抗压”，而是能用指标说明优化效果。

## 17. 增加可观测性和链路追踪

- 当前现状：各服务已经引入 Actuator、Micrometer Prometheus，也有日志注解和部分日志输出，但还可以进一步统一链路追踪和业务指标。
- 为什么值得改：购票链路跨网关、车票、订单、支付、MQ，排查问题时需要知道一个订单号或请求链路经过了哪些服务。
- 可以怎么改：接入 traceId，并在网关、Feign、MQ 消息中透传；为查票耗时、购票成功率、锁等待时间、MQ 消费失败、缓存命中率、订单关闭补偿次数增加指标；对异常订单建立告警。
- 改完能带来什么收益：线上排查更快，也能及时发现热点、堆积和一致性异常。
- 面试里可以怎么表达：这个项目的业务链路比较长，后续我会重点补可观测性，不只是看服务是否存活，还要看订单链路是否完整、MQ 是否堆积、缓存命中率是否下降。

## 18. 规范接口文档和错误码体系

- 当前现状：项目有统一返回 `Result`、全局异常和错误码基础类，但业务错误码、接口文档和前后端契约还可以更系统。
- 为什么值得改：购票、支付、订单状态异常很多，如果错误码不清晰，前端和用户很难知道下一步该做什么。
- 可以怎么改：整理统一错误码规范，区分参数错误、库存不足、重复提交、订单状态非法、支付失败、系统繁忙；补充 OpenAPI/Swagger 文档；关键接口标明幂等字段、登录要求和错误响应。
- 改完能带来什么收益：接口协作更清晰，前端处理更稳定，排查问题也更方便。
- 面试里可以怎么表达：后端工程不只是实现接口，还要让接口可协作、可定位。后续我会把错误码和接口文档补齐，尤其是购票失败和支付失败这类用户敏感场景。

# 六、如果继续迭代，这个项目可以怎么演进

## 19. 第一阶段：把核心购票链路打磨稳定

- 当前现状：项目已经能讲清楚从登录、查票、购票、订单、支付、超时关闭的主链路。
- 为什么值得改：核心链路是面试和系统价值的基础，先稳定主链路比盲目扩功能更重要。
- 可以怎么改：默认启用查票 V2；完善购票幂等和重复购买校验；补齐订单、支付、座位状态补偿；完善退款闭环。
- 改完能带来什么收益：项目主干更可靠，面试时也能更自信地讲完整业务闭环。
- 面试里可以怎么表达：如果继续迭代，我会先不急着加新功能，而是把核心购票链路做扎实，尤其是查票性能、购票并发、订单支付一致性。

## 20. 第二阶段：增强高并发能力和可靠消息

- 当前现状：项目已经有 Redis 缓存、Redisson 锁、RocketMQ、令牌桶雏形和 ShardingSphere 分片。
- 为什么值得改：这些能力已经有基础，但还可以从“能跑通”提升到“高峰期更可靠”。
- 可以怎么改：完整启用令牌桶；引入可靠消息机制；增加热点缓存治理；补充压测和监控；根据压测结果调整锁粒度、线程池和限流规则。
- 改完能带来什么收益：项目能更好地支撑春运类高并发场景，也能形成更深入的性能优化案例。
- 面试里可以怎么表达：第二阶段我会围绕高并发做深，不只是加锁，而是从入口限流、缓存热点、锁竞争、可靠消息和监控指标整体优化。

## 21. 第三阶段：扩展票务业务能力

- 当前现状：当前功能主要围绕普通购票和支付，复杂票务能力还可以继续补充。
- 为什么值得改：改签、候补、风控、对账这些能力更接近真实票务系统，也更能体现系统设计能力。
- 可以怎么改：增加改签流程、候补队列、支付对账、退款对账、用户风控；引入聚合服务支持复杂页面；把订单状态机作为统一业务底座。
- 改完能带来什么收益：项目从面试型购票系统逐步演进成更完整的票务交易平台。
- 面试里可以怎么表达：我对这个项目的演进理解是三步：先稳定主链路，再提升高并发和可靠性，最后扩展改签、候补、对账、风控等真实业务能力。这样项目不是简单堆技术，而是按业务复杂度逐步成长。
