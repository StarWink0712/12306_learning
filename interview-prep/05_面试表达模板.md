# 一、项目开场介绍模板

## 30 秒版本

我这个项目是一个模拟铁路 12306 核心购票链路的 Java 微服务项目。它不是普通后台管理系统，重点在用户登录、乘车人管理、车票查询、购票选座、订单创建、支付回调、超时关闭和退票退款这一整条链路。

项目用 Maven 多模块组织，业务服务主要有网关、用户、车票、订单、支付，公共能力比如缓存、幂等、统一异常、责任链、策略模式、用户上下文、分布式 ID 放在 `frameworks` 里。我主要围绕购票主流程、订单状态流转、缓存和并发控制去理解和整理。

## 1 分钟版本

这个项目可以理解成一个 12306 购票后端的学习和实现项目。核心场景是用户登录后查询车票，然后选择乘车人和席别进行购票，系统完成选座、锁座、创建待支付订单，之后用户支付，支付服务收到支付宝回调后通过 MQ 通知订单服务改订单状态，同时通知车票服务把座位状态改成已售。如果用户下单后 10 分钟没有支付，订单服务会通过 RocketMQ 延迟消息触发关闭订单，车票服务再释放座位和余票缓存。

我觉得这个项目比较值得讲的地方，不是单纯用了 Redis、RocketMQ、ShardingSphere，而是这些技术都对应到具体业务问题：查票是高频读，所以做缓存和 pipeline 优化；购票是高并发写，所以做责任链校验、细粒度锁和幂等；订单和支付是跨服务状态流转，所以用 MQ 和补偿思路保证最终一致。

## 如果面试官问“这是你自己做的吗”

这个项目是基于 12306 购票场景做的学习和二次实现整理，里面能看到一些开源学习项目的痕迹。我不会把它包装成完全从零原创的商业系统。我的重点是我确实把核心链路、源码实现、设计取舍、可能的问题和后续优化都梳理过，尤其是购票、订单、支付、缓存、并发和一致性这些部分。

# 二、介绍核心业务流程的模板

## 查票流程

查票这块我一般会从“为什么复杂”开始讲。它不是简单查一张车次表，因为用户输入的是出发地、目的地、出发站、到达站、日期，后端要返回车次列表、席别、价格、余票、发到站时间这些信息。

项目里 `TicketServiceImpl` 先通过责任链做参数和站点合法性校验，然后从 Redis 里取站点到地区的映射、地区到车次的映射，再组合车次信息、站点价格和区间余票。V1 版本是在循环里多次访问 Redis，容易有网络往返开销；V2 版本用 pipeline 批量取价格和余票，优化点主要是减少 Redis 交互次数。

我面试里会强调：查票优化的重点不是“用了 Redis”这么简单，而是根据数据变化频率拆缓存，静态数据长缓存，余票这种高变化数据单独维护。

## 购票流程

购票流程我会按“校验、加锁、选座、建单、支付前等待”来讲。

用户提交购票请求后，车票服务先走购票责任链，校验参数、车次、乘车人、余票和重复购买这类问题。然后 V2 版本会按座位类型分组，比如同一车次的商务座、一等座、二等座分开加锁，锁粒度是车次加席别。这里用了本地 `ReentrantLock` 和 Redisson 分布式锁，本地锁处理单实例竞争，分布式锁处理多实例竞争。

拿到锁后，系统会根据列车类型和座位类型走策略模式选座，选好后锁定座位，保存车票记录，再通过 Feign 调订单服务创建待支付订单。订单创建成功后会发 RocketMQ 延迟消息，如果用户超时不支付，就自动关闭订单并释放座位。

## 支付和回调流程

支付这块的流程是，支付服务创建支付单，然后通过支付宝沙箱生成支付请求。用户支付成功后，支付宝会回调支付服务。支付服务先更新自己的支付单状态，然后发送支付结果消息。

后面不是支付服务直接改所有数据，而是订单服务和车票服务分别消费支付结果消息。订单服务把订单和订单项改成已支付，车票服务把座位从锁定改成已售。这样每个服务维护自己的数据边界，支付服务只负责支付，不直接越权操作订单和座位。

## 超时关闭流程

这个项目里订单创建后会发送 RocketMQ 延迟消息，延迟级别是 10 分钟。消息到期后，车票服务消费这个消息，先远程调用订单服务关闭订单。

如果订单已经支付了，关闭会失败，系统就不释放座位。如果订单还是待支付，就说明用户超时未支付，这时系统会释放数据库中的座位状态，回滚 Redis 里的区间余票，也会回滚令牌桶相关数据。

我会补一句：真实生产里不能只依赖延迟消息，还应该有定时补偿任务，扫描超时未关闭订单。

# 四、回答技术选型问题的模板

## 为什么用 Redis

Redis 在这个项目里主要解决两个问题：一个是查票这种高频读场景，另一个是余票这种需要快速读写的数据。

像车站映射、车次信息、站点价格这些数据变化不频繁，适合缓存起来减少数据库压力；余票变化比较频繁，所以项目把它拆成区间和席别维度的 Hash 来维护。查票 V2 里还用了 pipeline，减少一次请求里多次访问 Redis 的网络往返。

所以我不会简单说“用 Redis 提高性能”，更准确地说，是根据票务数据的访问频率和变化频率做缓存拆分。

## 为什么用 RocketMQ

RocketMQ 主要用在跨服务异步状态流转上。最典型的是两个场景：订单超时关闭和支付结果通知。

订单创建后，系统发送延迟消息。10 分钟后如果订单还没支付，就关闭订单并释放座位。支付成功后，支付服务发送支付结果消息，订单服务消费后更新订单状态，车票服务消费后更新座位状态。

这样做的好处是支付、订单、车票之间不用强同步耦合，每个服务只处理自己负责的数据。当然，MQ 也会带来重复消费和消息可靠性问题，所以项目里用了幂等注解，后续还可以加本地消息表或事务消息。

## 为什么用 Redisson 锁

购票是典型并发写场景，同一车次、同一席别会有大量用户同时抢票。如果只靠普通 Java 锁，多实例部署下是不够的，所以项目用了 Redisson 分布式锁。

购票 V1 是按车次加锁，比较保守；V2 进一步按车次加席别加锁，减少不同席别之间不必要的阻塞。同时项目还用了本地锁，主要是减少同一个 JVM 内线程对分布式锁的竞争。

我会强调，锁不是越粗越安全，也不是越细越好，关键是和业务资源粒度匹配。

## 为什么用 ShardingSphere

订单和支付数据是持续增长的数据，尤其订单查询有用户维度、订单号维度，支付查询有订单号和支付流水号维度。项目里订单服务和支付服务使用 ShardingSphere 做分库分表。

订单表和订单项表按 `user_id` 和 `order_sn` 复合分片，支付表按 `order_sn` 和 `pay_sn` 分片。这样是为了让常见查询尽量命中明确分片，降低单库单表压力。

另外订单项里的身份证号和手机号还配置了 AES 加密，这说明项目也考虑了敏感数据存储问题。

## 为什么用责任链和策略模式

责任链主要用在校验流程，比如用户注册、查票、购票、退票。因为这些流程都有多个校验步骤，如果都写在一个方法里，后面会很难维护。拆成责任链后，可以按顺序执行，也方便新增校验。

策略模式主要用在选座和支付。不同车型、不同席别的选座规则不一样，不同支付渠道的请求和回调也不一样。用策略模式后，主流程只负责选择策略，不需要写一堆 if-else。

我会说，这里不是为了炫设计模式，而是因为业务规则本身会扩展。

# 五、回答深度追问的模板

## 被问“如何防止超卖”

我会从三个层面回答。

第一层是入口校验，购票前会走责任链，先校验参数、乘车人、余票和重复购买。

第二层是并发控制，购票 V2 按车次和席别加锁，避免多个请求同时分配同一类座位。锁内执行选座和座位状态更新。

第三层是资源回滚，订单超时未支付或取消时，会释放座位、回滚 Redis 余票和令牌桶。这样不是单纯扣一个库存数字，而是围绕座位状态和区间余票做控制。

如果被继续追，我会补充：项目里也保留了令牌桶 Lua 脚本方案，但当前主链路更明确的是锁、选座、座位状态和缓存扣减，令牌桶可以作为后续前置限流优化。

## 被问“跨服务一致性怎么保证”

这个项目没有把所有跨服务操作放到一个强一致分布式事务里，而是用了本地事务加消息加补偿的思路。

比如购票时，车票服务负责锁座和保存车票记录，订单服务负责创建订单。订单创建后通过延迟消息处理超时未支付的释放。支付成功后，支付服务通过 MQ 通知订单和车票服务分别更新自己的状态。

我会承认这里还有生产化优化空间，比如可以加本地消息表或 RocketMQ 事务消息，保证业务数据变更和消息投递更可靠；再加补偿任务扫描异常订单和异常座位状态。

## 被问“缓存和数据库不一致怎么办”

我会先说当前项目的主流程：购票成功会扣减 Redis 里的区间余票，取消或超时关闭会回滚 Redis 余票，同时座位状态在数据库里维护。

项目里还保留了 Canal binlog 同步余票缓存的方案，可以根据 `t_seat` 的状态变化异步修正 Redis。更完整的生产方案，我会设计成“业务实时扣减 + binlog 异步校准 + 定时对账补偿”。这样即使某一步失败，也有后续校准机制。

## 被问“有锁了为什么还要幂等”

锁和幂等解决的问题不一样。

锁解决的是多个请求同时争抢同一份资源，比如同一车次同一席别的座位。幂等解决的是同一个业务请求重复执行，比如用户重复点击购票、支付创建重复提交、MQ 消息重复消费。

所以项目里既有 Redisson 锁控制购票并发，也有 `@Idempotent` 控制重复提交和重复消费。两个不是互相替代，而是保护不同风险点。

## 被问“V1/V2 有什么区别”

查票的 V1 和 V2，主要区别是 Redis 访问方式。V1 在循环里逐个查价格和余票，网络往返次数多；V2 把 key 批量构造出来，用 pipeline 批量获取，减少 Redis 交互次数。

购票的 V1 和 V2，主要区别是锁粒度。V1 按车次加锁，比较粗；V2 按车次加席别加锁，同时组合本地锁和分布式锁，并发度更高。

面试时我会注意说清楚：当前 Controller 查票默认还是 V1，V2 是已经实现的优化方案，后续上线应该切换并压测验证。

# 六、回答“如果继续优化你会怎么做”的模板

## 简洁版本

如果继续优化，我会按三个阶段来做。

第一阶段先把核心链路打稳，比如查票默认切到 V2，补齐重复购买校验，完善退款返回和订单状态机。

第二阶段增强高并发和稳定性，比如完整启用令牌桶，补本地消息表或事务消息，增加异常状态补偿任务，监控锁等待、MQ 堆积、缓存命中率。

第三阶段扩展业务深度，比如改签、候补、支付对账、退款对账、风控和聚合服务。

## 展开版本

我不会一上来就说重构架构，而是先按业务优先级来。

最优先的是核心链路稳定性。比如查票 V2 已经实现了 pipeline 优化，但入口还可以切换过去；退款链路目前有基础实现，但返回和状态流转还可以补完整；订单状态可以从枚举和分散判断升级成更明确的状态机。

第二块是可靠性。订单超时关闭、支付结果通知都依赖 MQ，后续可以加本地消息表或事务消息，避免数据库状态变了但消息没可靠发出去。同时增加补偿任务，扫描支付成功但订单没更新、待支付超时没关闭、座位锁定太久没释放这些异常。

第三块是性能。查票可以继续做热点缓存、本地缓存和请求合并；购票可以完整启用令牌桶作为前置限流；再通过压测看锁粒度、线程池、Redis key 热点有没有瓶颈。

这样回答的重点是：我不是为了优化而优化，而是按主链路、可靠性、性能、业务扩展逐步演进。

# 七、回答“项目有哪些不足”的模板

## 稳妥版本

这个项目我觉得更适合说是一个面向 12306 核心购票场景的学习和实践项目，主链路比较完整，但离真正生产级系统还有一些可以补的地方。

比如退款链路还可以更完整，当前有些返回和状态流转没有完全补齐；查票 V2 已经实现，但默认入口还可以切换；MQ 这块目前用了延迟消息和支付回调消息，但可靠投递还可以用本地消息表或事务消息增强；还有一些本地配置，比如数据库密码、支付宝沙箱密钥，正式环境应该放到配置中心或密钥管理系统里。

我不会回避这些点，因为这些其实也是我复盘项目时重点思考的方向。我的理解是，这个项目现在能很好地说明我对购票业务、缓存、并发、订单和支付一致性的理解，后续就是继续把可靠性、工程化和业务完整度补上。

## 如果面试官质疑“这不就是课程项目吗”

可以这样回答：

确实，这个项目有学习项目和开源项目的痕迹，我不会把它说成完全原创的商业系统。但我准备这个项目的重点不是背代码，而是把里面的核心链路真正拆开理解。

比如为什么查票要拆缓存，为什么购票不能只扣一个库存，为什么座位要按区间占用，为什么支付成功要异步通知订单和车票，为什么有锁还要幂等，为什么 MQ 还要补偿。这些问题我都按源码和业务流程梳理过。

所以我更希望通过这个项目说明两点：第一，我能读懂一个相对复杂的 Java 微服务项目；第二，我能把业务问题、代码实现和后续优化思路串起来，而不是只停留在 CRUD。
